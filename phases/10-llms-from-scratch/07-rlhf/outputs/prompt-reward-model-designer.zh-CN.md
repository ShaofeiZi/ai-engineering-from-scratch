# 奖励模型设计器

在构建 RLHF 流水线以将语言模型对齐到目标行为（有用性、编程能力、安全性、诚实性）时，使用该框架来设计数据采集协议、训练奖励模型并配置 PPO。

## 输入要求

提供以下信息：
- **目标行为**（例如"有用且无害的助手"、"Python 专家编程助手"、"带安全约束的医疗问答"）
- **基础模型**（例如 SFT 之后的 Llama 3 8B、Mistral 7B Chat）
- **奖励模型规模**（通常与策略模型相同或更大）
- **标注预算**（可用的人工工时或比较对数量）
- **算力预算**（用于奖励模型训练 + PPO 的 GPU 小时数）

## 步骤 1：偏好数据采集

### 标注协议

1. **提示词选择**：从 SFT 训练分布中采样，并加入分布外提示词（10-20% 为新提示）
2. **响应生成**：使用 SFT 模型为每个提示词生成 2-4 个响应，采用不同温度（0.3、0.7、1.0）
3. **比较格式**：向标注者展示恰好 2 个响应，询问"哪个响应更好？"
4. **评分准则**：针对你的用例定义"更好"的含义

### 评分准则模板

| 准则 | 权重 | 描述 |
|-----------|--------|-------------|
| 有用性 | 40% | 是否完整且正确地回答了问题？ |
| 无害性 | 25% | 是否避免有害、偏颇或误导性内容？ |
| 诚实性 | 20% | 是否承认不确定性而非胡编乱造？ |
| 简洁性 | 15% | 响应长度是否与问题相称？ |

根据你的用例调整权重。编程助手可能将正确性权重设为 60%，简洁性设为 20%。

### 数据规模指南

| 规模 | 比较对数量 | 标注工时 | 预期 RM 准确率 |
|-------|-----------------|-----------------|---------------------|
| 最低可用 | 5,000-10,000 | 400-800 | 60-65% |
| 生产 v1 | 20,000-50,000 | 1,600-4,000 | 65-72% |
| 生产 v2 | 100,000-500,000 | 8,000-40,000 | 72-78% |

InstructGPT 使用了来自 40 名承包商的 33,000 次比较。Anthropic 最初的论文使用了来自 20 名标注者的 22,000 次比较。标注者之间的一致率通常为 70-75%——奖励模型无法超过人类一致率水平。

### 质量控制

- **一致率过滤**：当少于 70% 的标注者达成一致时，丢弃该比较对
- **标注者校准**：在正式标注前，使用已知优质的比较对进行校准轮次
- **偏置检测**：监控标注者是否持续偏好更长的响应、正式用语或特定模式
- **对抗样本**：加入 5-10% 专门用于识别不认真阅读的标注者的样本

## 步骤 2：奖励模型架构

### 架构决策

| 决策 | 建议 | 理由 |
|----------|---------------|-----------|
| 基础架构 | 与策略相同的 transformer | 从 SFT 检查点初始化权重提供强大的起始特征 |
| 输出头 | 从最后一个隐藏状态出发的单一线性投影 | 从最完整的位置表示产生标量奖励 |
| 模型规模 | >= 策略模型规模 | 较小的 RM 产生不可靠信号，使 PPO 不稳定 |
| 初始化 | 使用新的输出头的 SFT 检查点 | 预训练特征已经捕获了语言质量 |

### 训练配置

| 参数 | 范围 | 备注 |
|-----------|-------|-------|
| 学习率 | 1e-5 to 5e-5 | 比 SFT 低，因为任务更简单 |
| 轮次 | 1-3 | 在比较数据有限的情况下，过拟合是主要风险 |
| 批大小 | 64-256 | 每个"样本"是一对，因此有效数据量是 2 倍 |
| 损失函数 | Bradley-Terry: -log(sigmoid(r_preferred - r_rejected)) | 成对比较的标准做法 |
| 验证集划分 | 10-20% | 在留出对上监控准确率 |

### 评估指标

1. **成对准确率**：RM 在留出的偏好对中正确排序的比例是多少？目标：> 65%
2. **边界分布**：绘制 (r_preferred - r_rejected) 的分布。应以 0 以上为中心，负值很少。
3. **校准**：sigmoid(r_preferred - r_rejected) 是否接近实际的人类偏好概率？
4. **OOD 泛化**：在与训练不同的分布的提示词上测试。准确率下降应 < 10%。

## 步骤 3：PPO 配置

### 超参数

| 参数 | 典型值 | 过高的影响 | 过低的影响 |
|-----------|--------------|-------------------------|------------------------|
| KL 系数 (beta) | 0.01-0.05 | 模型几乎不学习，过于贴近 SFT | 奖励黑客，退化输出 |
| 学习率 | 5e-6 to 3e-5 | 训练不稳定，发散 | 收敛缓慢，浪费算力 |
| 裁剪比率 (epsilon) | 0.1-0.3 | 过大、可能不稳定的更新 | 过于保守的更新，学习缓慢 |
| 每批 PPO 轮次 | 1-4 | 对当前批次过拟合 | 未充分利用每个批次 |
| 生成批大小 | 128-512 | 内存问题 | 梯度估计噪声大 |
| 最大响应长度 | 256-1024 | 生成缓慢，内存问题 | 截断有用的响应 |

### 监控仪表板

在 PPO 训练期间跟踪以下指标：

1. **平均奖励**：应在训练过程中上升。停滞没问题；下降意味着不稳定。
2. **KL 散度**：应保持在 10-20 nats 以下。飙升 = 奖励黑客。
3. **响应长度**：应保持稳定。单调增长 = 冗长奖励黑客。
4. **熵**：token 分布熵应缓慢下降。快速下降 = 模式崩溃。
5. **奖励模型一致率**：用奖励模型对 PPO 响应评分；一致率应提升。

### PPO 期间的警示信号

| 症状 | 可能原因 | 修复方法 |
|---------|-------------|-----|
| 奖励上升但输出退化 | 奖励黑客 | 提高 KL 系数，在对抗样本上重新训练 RM |
| KL 散度爆炸 | 学习率过高或 KL 系数过低 | 降低 lr，提高 beta |
| 响应长度单调增长 | RM 奖励冗长 | 在奖励中加入长度惩罚，用长度受控的对重新训练 RM |
| 所有响应变得相同 | 模式崩溃 | 提高生成温度，减少 PPO 轮次 |
| 奖励剧烈震荡 | PPO 不稳定 | 降低学习率，提高裁剪比率 |

## 步骤 4：端到端验证

在部署 RLHF 训练的模型之前：

1. **对比 SFT 做 A/B 测试**：在 200+ 测试提示上运行 SFT 和 RLHF 模型。由 3+ 名评估者比较响应。RLHF 模型应在 > 60% 的情况下胜出。
2. **安全评估**：在已知对抗提示（越狱、有害请求）上测试。RLHF 模型应适当拒绝。
3. **回归检查**：运行标准基准（MMLU、HumanEval、MT-Bench），确认 RLHF 模型没有丢失核心能力。
4. **遗忘检查**：在通用文本语料上测量困惑度。相对于 SFT 模型增长应 < 10%。
5. **长度分析**：比较 SFT 和 RLHF 模型之间的平均响应长度。如果 RLHF 长 > 50%，奖励模型可能有冗长偏置。
