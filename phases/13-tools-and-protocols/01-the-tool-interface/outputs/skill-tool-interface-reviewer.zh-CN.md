给定一个拟议的工具定义，对照四步循环（描述、决策、执行、观察）进行审查，并在该工具到达模型之前标记出破坏循环的缺陷。

产出：

1. 名称审计。名称是否为 `snake_case`、跨版本稳定且无歧义？标记与内建名称冲突、包含时态（"was_"、"will_"）或内嵌参数的名称。
2. 描述审计。描述是否读起来像一份完整的使用说明？要求采用双句格式："在 X 时使用。不要用于 Y。" 标记少于 40 个字符的描述、营销式行文，以及任何不能指导选择的描述。
3. Schema 审计。该 schema 是否为有效的 JSON Schema 2020-12？每个字段是否都有类型？`required` 列表是否显式声明？对于封闭值集是否使用了枚举？标记本应为枚举的开放式字符串字段、缺失类型，以及输入对象上未声明的 `additionalProperties`。
4. 执行器审计。给定参数后执行器是否确定？是否以带类型的错误处理失败（而非抛出逃逸出宿主的异常）？如果它是后果性的（变更状态、花费金钱、接触用户数据），是否被标记为此类并设置了确认门控？
5. 分类。说明该工具是纯函数性的还是后果性的，并给出理由。一个后果性工具如果没有门控，则立即拒绝。

硬性拒绝：
- 任何描述只说明做什么而不说明何时使用的工具。模型在第二步需要"何时"。
- 任何含有未类型化字段的 schema。验证器无法完成其工作。
- 任何同时满足以下三项的工具：接受不可信输入、读取敏感数据、采取后果性动作。违反了 Meta 的 Rule of Two。
- 任何执行器在错误输入时抛出未处理异常的工具。宿主不应在每次调用外都套一层 try/except。

拒绝规则：
- 如果工具定义缺少 schema，拒绝。引导至 Phase 13 · 04。
- 如果工具是纯函数性的，但描述中写着"谨慎使用"，拒绝并询问原因。纯函数性工具的重复运行成本应很低。
- 如果被要求批准的工具在未设置只读守卫的情况下连接生产数据库，拒绝并引导至 Phase 13 · 17（网关与策略）。

输出：一份单页审计报告，列出名称、描述、schema 和执行器的发现，附严重程度（block / warn / nit），以及最终裁定（ship / revise / reject）。对于任何被拒绝的工具，如果可行，以一行改写建议结尾。
