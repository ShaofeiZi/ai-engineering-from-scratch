给定一个内部平台需求，设计一个无状态 MCP 服务器及治理边界，目标协议修订版本为 `2026-07-28`。

构建计划：

1. 一个模式合法的 `server.json`，其反向 DNS 名称与发布者已验证的命名空间匹配。
2. 必需的 `server/discover`，用于实时版本、能力、扩展和服务器标识。
3. 每个请求的 `_meta` 中包含版本和客户端能力；每个结果中包含 `resultType` 和服务器标识。
4. 确定性的 `tools/list`，附带 `ttlMs` 和 `cacheScope`。
5. 仅 POST 的 Streamable HTTP，包含必需的版本、方法和名称头；无协议会话、GET 流、会话 DELETE 或重放头。
6. 在每次调用时验证签发者、受众、过期时间和作用域的授权。
7. 对参与者、工具、目标和归一化参数实施策略。将高风险审批绑定到精确的操作和过期时间，然后证明更改任一参数即可拒绝重放。
8. 在模型可见上下文之外进行脱敏的审计和追踪证据。
9. 一个注册表适配器，用于校验 `server.json`、探测 `server/discover`，并报告元数据/运行时漂移。
10. 两个可互换的副本和一个并发负载探测，无会话亲和性。

评估标准：

| 权重 | 标准 | 度量 |
|:-:|---|---|
| 25 | 协议正确性 | 无状态信封、发现、结果、头部和否定用例 |
| 20 | 授权 | 签发者、受众、过期时间、作用域和精确操作审批用例 |
| 15 | 注册表完整性 | 合法的 `server.json`、实时探测和漂移报告 |
| 15 | 策略与安全 | 允许、拒绝、格式错误、过期审批和敏感数据用例 |
| 15 | 规模 | 两个副本无亲和性依赖，加上取消和恢复 |
| 10 | 可审计性 | 接收方侧脱敏的审计和追踪证据 |

硬性否决项：

- 使用 `initialize`、`notifications/initialized` 或 `Mcp-Session-Id` 的当前 MCP 设计。
- 将 `server.json` 视为实时能力发现，或编造 `.well-known/mcp-capabilities` 作为 MCP 要求。
- 在该发布者已验证命名空间之外发布服务器名称。
- 在未验证签发者和受众或资源的情况下接受令牌。
- 将工具注解或聊天审批视为授权。
- 持久化密钥或原始敏感数据的审计记录。

拒绝规则：

- 拒绝仅凭本地模拟就声称已达到生产就绪。
- 拒绝在缺少策略和操作绑定审批证据的情况下暴露有状态变更工具。
- 拒绝发布指向无法验证实时发现的端点的元数据。

输出：一份构建计划和证据矩阵，涵盖发布元数据、实时发现、无状态传输、工具模式、授权、策略、审批、审计和规模。以最高风险边界和证明其故障安全的精确失败测试结尾。
