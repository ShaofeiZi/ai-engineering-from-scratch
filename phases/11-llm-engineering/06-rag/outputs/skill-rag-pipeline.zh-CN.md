# RAG 流水线模式

每个 RAG 系统都遵循以下模式：

```
documents -> chunk -> embed -> store
query -> embed -> search(top_k) -> build_prompt -> generate
```

索引对每个文档只执行一次。查询则在每次用户请求时执行。

## 何时使用 RAG

- LLM 需要访问私有或最新文档
- 微调成本过高或更新太慢
- 你需要为答案引用来源
- 知识库频繁变更

## 何时不使用 RAG

- 答案是 LLM 已掌握的通用知识
- 任务偏向创意（写作、头脑风暴）而非事实
- 你需要模型采用特定的推理风格（应使用微调）

## 实现清单

1. 将文档切分为 256-512 token 的片段，片段间保留 50 token 重叠
2. 使用一致的嵌入模型对每个片段生成嵌入
3. 将嵌入与原始文本一起存入向量数据库
4. 查询时，用同一模型对用户问题生成嵌入
5. 通过余弦相似度检索最相似的 top-k（5-10）个片段
6. 构建提示词：系统指令 + 检索到的上下文 + 用户问题
7. 生成答案，并使其基于检索到的上下文
8. 返回答案及其来源引用

## 常见错误

- 索引和查询使用不同的嵌入模型（向量不兼容）
- 片段过小（丢失上下文）或过大（稀释相关性）
- 片段之间不设置重叠（在边界处切断句子）
- 文档变更后忘记重建索引
- 把检索到的片段直接返回给用户，而没有生成连贯的答案
- 事实型 RAG 查询未设置 temperature=0（温度越高，幻觉越多）

## 检索调试

如果正确的片段未被检索到：
1. 打印查询嵌入，确认其非零
2. 对一个已知相关的片段手动检查余弦相似度
3. 尝试改写查询，使其与文档用词匹配
4. 确认索引时和查询时使用的是同一个嵌入模型
5. 检查相关内容是否在分片过程中丢失

## 生产环境参数

- 片段大小：256-512 token
- 重叠：50 token（片段大小的 10-20%）
- Top-k：大多数场景取 5-10
- Temperature：事实型答案取 0
- 嵌入模型：text-embedding-3-small（成本较低）或 text-embedding-3-large（精度更高）
