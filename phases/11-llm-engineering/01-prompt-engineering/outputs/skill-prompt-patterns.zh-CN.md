# 提示词模式选择指南

在构建基于 LLM 的功能时，先选择提示词模式，再编写提示词。模式决定结构，内容填充其中。

## 模式决策矩阵

| 任务类型 | 主模式 | 辅助模式 | Temperature | 需要 Few-shot？ |
|-----------|----------------|-------------------|-------------|-----------------|
| 数据抽取 | 模板填充 | Few-Shot | 0.0 | 是（2-3 个示例） |
| 分类 | Few-Shot | 护栏 | 0.0 | 是（3-5 个示例） |
| 摘要 | 人设 + 模板 | 受众适配 | 0.3 | 否 |
| 代码生成 | 人设 | Chain-of-Thought | 0.0 | 可选 |
| 创意写作 | 人设 | 批判 | 0.7-1.0 | 否 |
| 多步推理 | Chain-of-Thought | 分解 | 0.3 | 可选 |
| 问答 | 人设 + 护栏 | 边界 | 0.3 | 否 |
| 提示词生成 | 元提示 | 批判 | 0.7 | 是（1-2 个示例） |
| 内容审核 | 护栏 + 边界 | Few-Shot | 0.0 | 是（5+ 个示例） |
| 翻译/改编 | 受众适配 | Few-Shot | 0.3 | 是（2-3 个示例） |

## 何时使用每种模式

**人设模式**：作为基线用于每一条提示词。唯一的问题是把角色设定到多具体。对于通用任务，宽泛的角色即可；对于领域专属任务，角色应点明领域、资历级别和上下文。

**Few-Shot 模式**：当输出格式比内容更重要时使用。如果模型需要产出特定的 JSON 形状、CSV 格式或分类标签，示例比指令更有效。经验法则：简单格式 2-3 个示例，复杂或模糊格式 5+ 个示例。

**Chain-of-Thought 模式**：用于数学、逻辑、多步分析，以及任何需要模型"展示推理过程"的任务。在推理任务上可提升 10-40% 的准确率（Wei et al., 2022）。不要用于简单的事实查询或抽取——那会浪费 token。

**模板填充模式**：用于每个输出都必须具有相同形状的结构化抽取。在 temperature=0.0 下效果最佳，并对缺失字段显式处理 "N/A"。

**批判模式**：当质量比速度更重要时使用。模型先生成、再批判、最后改进。大约会使 token 成本翻倍，但显著提升准确性和完整性。最适合高风险输出（报告、建议、面向公众的内容）。

**护栏模式**：用于任何面向用户的系统。始终包含：范围边界、对越界请求的拒绝行为，以及明确的"我不知道"处理。与应用侧的输入校验配合使用。

**元提示模式**：用于为新任务生成提示词。不必从零编写提示词，而是描述任务让模型来写。然后测试和迭代。可节省初始提示词开发的时间。

**分解模式**：用于受益于分而治之的复杂问题。模型将问题拆分为子问题、逐个求解，再合并结果。对包含 3-7 个子问题的任务最有效。

**受众适配模式**：当相同内容需要服务不同受众时使用。明确指定受众——不要依赖模型从上下文中猜测。

**边界模式**：用于绝不能回答某些类型问题的生产系统。比护栏更强，因为它定义了硬性范围和精确的拒绝消息。对合规敏感领域不可或缺。

## 跨模型兼容性

按模式在 GPT-4o、Claude 3.5 Sonnet、Gemini 1.5 Pro 和 Llama 3 之间一致生效的程度排序：

| 模式 | 跨模型一致性 | 备注 |
|---------|------------------------|-------|
| Few-Shot | 非常高 | 示例在所有模型上都迁移良好 |
| 模板填充 | 非常高 | 显式结构几乎不留分歧空间 |
| Chain-of-Thought | 高 | 所有主流模型都支持 "think step by step" |
| 人设 | 高 | 到处都有效，但不同模型对角色具体程度的响应不同 |
| 护栏 | 中等 | Claude 最严格遵守护栏；GPT-4o 在长对话中有时会漂移 |
| 批判 | 中等 | 自我批判的质量因模型而异，差异显著 |
| 元提示 | 中等 | GPT-4o 和 Claude 产出的提示词风格不同 |
| 边界 | 中低 | 拒绝行为各异；需按模型测试 |

## 常见错误

1. **处处使用 Chain-of-Thought**：CoT 增加 token 和延迟。仅在需要推理步骤时使用。
2. **约束过多**：超过 5-7 条约束后模型开始丢弃部分约束。优先保留最重要的 3 条。
3. **人设与约束矛盾**："You are a creative writer" + "Never use metaphors" 会让模型困惑。
4. **未指定温度**：在需要确定性输出时把温度留在默认值（通常是 1.0）。
5. **跨模型复制粘贴提示词**：务必测试。为 GPT-4o 调优的提示词在 Claude 上可能表现不佳，反之亦然。
6. **忽视 system 消息**：把所有内容都塞进 user 消息，而不使用 system 消息承载持久规则。
7. **过度依赖负向约束**："Do NOT do X, Y, Z, A, B, C" 不如 "ONLY do W" 有效。正向表述给模型一个清晰的目标。

## 可靠性目标

| 用例 | 模式组合 | 预期准确率 | Token 成本 |
|----------|-------------------|-------------------|------------|
| 生产级抽取 | 模板 + Few-Shot | 95%+ | 低（500-1K） |
| 面向用户的问答 | 人设 + 护栏 + 边界 | 90%+ | 中（1-2K） |
| 代码生成 | 人设 + Chain-of-Thought | 85%+ | 中（1-3K） |
| 内容生成 | 人设 + 批判 | 90%+ 质量 | 高（2-4K，两轮） |
| 分类 | Few-Shot + 护栏 | 95%+ | 低（300-800） |
| 复杂分析 | 分解 + Chain-of-Thought | 85%+ | 高（3-5K） |
