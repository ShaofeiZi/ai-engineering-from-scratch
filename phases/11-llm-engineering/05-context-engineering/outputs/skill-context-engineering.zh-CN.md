# 上下文工程

在构建 LLM 应用时，应用此框架来设计上下文组装流水线。

## 核心原则

1. **上下文是稀缺资源。** 一个 128K 窗口听起来很大，但很快就会被填满。显式地为每个组件做预算。
2. **注意力是不均匀的。** 模型更多关注开头和结尾。把关键信息放在那里。中间是死区。
3. **动态胜于静态。** 不同的查询需要不同的上下文。按查询逐次组装，而不是在启动时一次性组装。
4. **少即是多。** 精选的 10K 上下文胜过倾倒的 100K 上下文。信噪比比总信息量更重要。
5. **度量一切。** 你无法优化你没有度量的东西。在每次请求中按组件统计 token。

## 上下文预算指南

| 组件 | 典型范围 | 优先级 | 压缩策略 |
|-----------|-------------|----------|---------------------|
| System prompt | 200-1,000 tokens | 固定，高 | 写得紧凑，去除冗余 |
| Tool definitions | 500-3,000 tokens | 动态，中 | 按查询意图裁剪 |
| Retrieved context | 1,000-5,000 tokens | 动态，高 | 重排序 + 阈值 + 去重 |
| Conversation history | 500-5,000 tokens | 动态，中 | 摘要旧轮次 |
| Few-shot examples | 500-2,000 tokens | 动态，高 | 按任务相似度选择 |
| User query | 50-500 tokens | 固定，最高 | N/A |
| Generation reserve | 2,000-8,000 tokens | 固定 | 按预期输出长度调整 |

## 何时使用每种记忆类型

**短期记忆（对话历史）**：当前会话。通过摘要管理。压缩超过 5-10 轮交互的轮次。逐字保留最后 3-4 轮。

**长期记忆（事实数据库）**：跨会话持久化的偏好和项目事实。在会话开始时检索。例如：“用户偏好 Python”“项目使用 PostgreSQL”“团队采用主干开发”。存储在 CLAUDE.md、数据库或结构化记忆系统中。

**情景记忆（过往交互）**：与当前任务相关的特定过往对话。存为嵌入，按相似度检索。“上周我们调试过一个类似的鉴权问题”就是情景记忆。

## 工具选择策略

不要在每次请求中都包含所有工具。这会浪费 token 并让模型困惑。

1. 对查询意图进行分类（代码、邮件、日历、研究、数据）
2. 将意图映射到工具类别
3. 仅包含匹配的工具
4. 如果意图不明确，包含排名前 2 个类别的工具
5. 始终包含一个“通用”工具（如网页搜索）作为兜底

预期节省：在意图明确的查询上可节省 60-80% 的工具定义 token。

## 检索最佳实践

- **检索后重排序。** 向量相似度只是粗筛。重排序器（交叉编码器或基于 LLM）能显著提升精确率。
- **设定相关性阈值。** 不要纳入余弦相似度低于 0.3 的分块。它们只会增加噪声。
- **去重。** 如果两个分块有 80%+ 的内容相同，只保留得分更高的那个。
- **应用“中间迷失”排序。** 将最相关的分块放在最前和最后。
- **限制总检索 token。** 3-5 个高度相关的分块胜过 15 个平庸的分块。

## 历史管理

- 逐字保留最后 3-4 轮（模型需要近期上下文）
- 将更早的轮次摘要为一份摘要（“我们讨论了 X，决定了 Y，并阻塞于 Z”）
- 丢弃不增加信息的系统生成轮次（对用户无可见内容的工具调用）
- 当历史超过可用预算的 30% 时触发压缩

## 危险信号

- 系统提示超过 2,000 tokens：可能包含了本应动态化的信息
- 每次请求都包含所有工具：实现基于意图的选择
- 检索无相关性过滤：你在向窗口里倾倒噪声
- 历史无界增长：未实现摘要
- 无生成预留：模型会截断其回复
- 同一信息出现在 3 处（系统提示、检索文档、历史）：去重
- 上下文利用率超过 60%：你给模型留的“思考”空间太少
