# 嵌入模式

每个嵌入工作流都遵循这一契约：

```
text -> embed(text) -> vector (float array)
similarity(vector_a, vector_b) -> score (float)
```

嵌入模型和相似度度量是唯一两项重要决策。其余皆为配套工程。

## 何时使用嵌入

- 跨文档的语义搜索（查找语义，而非关键词）
- 聚类相似条目（支持工单、产品评论、缺陷报告）
- 基于最近邻的分类（通过与已标注示例的相似度标注新条目）
- 推荐系统（查找与用户已喜欢内容相似的条目）
- 去重（使用相似度阈值查找近似重复内容）

## 何时不使用嵌入

- 精确关键词匹配（使用全文搜索）
- 结构化查询（使用 SQL、过滤器）
- 手动标注更快捷的小型数据集（<100 条目）
- 可解释性比准确率更重要的任务（嵌入是不透明的）

## 模型选择

根据你的约束进行选择：

- **需要 API，性价比最高**：OpenAI text-embedding-3-small（1536d，$0.02/1M tokens）
- **需要最高准确率**：Voyage-3（1024d，$0.06/1M tokens，MTEB 最高）
- **需要本地/私密**：BGE-M3（1024d，免费，多语言，推荐使用 GPU）
- **需要快速本地原型开发**：all-MiniLM-L6-v2（384d，免费，可在 CPU 上运行）
- **需要多语言**：Cohere embed-v3（1024d）或 BGE-M3（两者多语言能力都很强）

规则：在索引与查询之间绝不要混用嵌入模型。来自不同模型的向量存在于不兼容的空间中。

## 分块规则

1. 每个分块目标为 256-512 tokens，重叠 50 tokens
2. 尽量避免在句子中间切分
3. 每个分块都附带元数据（源文件、章节标题、位置）
4. 对于结构化文档（Markdown、HTML），首先在标题边界处切分
5. 通过搜索已知答案并检查检索结果来测试分块质量

## 相似度度量选择

- **余弦相似度**：默认选择，可处理变长文本，已归一化
- **点积**：当向量已是单位归一化时使用（OpenAI 模型即是如此），略快
- **欧几里得距离**：用于聚类，当绝对位置重要时使用

当向量已归一化时，这三种度量给出的排序完全相同。该选择只对未归一化的向量才有影响。

## 存储优化

三个层级的压缩，可叠加使用：

1. **Matryoshka 截断**：降低维度（1536 -> 256 = 节省 6 倍，准确率下降 3-5%）
2. **Float16 量化**：每个维度存储减半（节省 2 倍，准确率下降 <1%）
3. **二值量化**：每个维度 1 比特（节省 32 倍，准确率下降 5-10%，需配合重排序使用）

生产模式：在整个语料上做二值搜索，再用 float32 向量对前 1000 条结果重打分。

## 检索后重排序

用于获得最佳准确率的两阶段流水线：

1. 双编码器检索前 100 个候选（快速，使用预计算的嵌入）
2. 交叉编码器重排序到前 10（较慢，逐对处理查询-文档对）

这比单阶段检索在精确率指标上高出 10-15%。当准确率比延迟更重要时使用。

## 常见错误

- 索引和查询使用不同的嵌入模型
- 嵌入整篇文档而非分块（嵌入会变成所有内容的平均）
- 在做余弦相似度前未归一化向量（大多数模型已预归一化，但需核实）
- 忽略分块重叠（在边界处被切分的句子会丢失上下文）
- 只存储向量而不保留原始文本（检索时两者都需要）
- 模型变更时未重新嵌入（旧向量不兼容）
- 仅基于准确率选择维度（存储和延迟与维度呈线性关系）

## 调试嵌入

如果搜索结果不佳：

1. 核实查询嵌入非零（空输入或空白输入会产生零向量）
2. 手动检查一份已知相关文档的相似度得分
3. 尝试改写查询以匹配文档词汇
4. 检查分块边界，确保相关内容未被切分到不同分块
5. 比较各度量（余弦、点积、欧几里得）的 top-k 结果以发现归一化问题
6. 用一个平凡匹配的查询测试（从文档中复制一句话）以确认流水线正常工作

## 生产参数

- 分块大小：256-512 tokens
- 分块重叠：50 tokens（分块大小的 10-20%）
- Top-k 检索：直接使用取 5-10，重排序取 50-100
- 相似度阈值：余弦相似度 0.7+（低于此值，结果通常无关）
- 批量嵌入：每次 API 调用处理 100-500 条文本以提升吞吐
- 索引重建：当模型变更或文档显著更新时重新嵌入
