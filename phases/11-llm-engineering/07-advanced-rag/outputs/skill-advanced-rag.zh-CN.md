# 进阶 RAG 模式

基础 RAG：嵌入查询 -> 向量检索 -> top-k -> 生成。
进阶 RAG：嵌入查询 + BM25 -> 融合排名 -> 重排序 -> top-k -> 生成。

```
query -> [vector search (top-50)] -+-> RRF fusion -> reranker (top-5) -> prompt -> LLM
                                   |
query -> [BM25 search (top-50)]  --+
```

## 何时从基础 RAG 升级

- 检索质量 Recall@5 降到 70% 以下
- 用户反馈答案错误或无关
- 语料规模超过 10 万个片段
- 查询使用的词汇与文档不一致
- 多跳问题持续失败

## 实现清单

1. 在向量索引之外再建立 BM25 索引
2. 并行执行两种检索（各取 top-50）
3. 用 Reciprocal Rank Fusion（k=60）合并
4. 用 cross-encoder 对候选片段重排序
5. 取 top-5 构建最终提示词
6. 在测试集上加入忠实度评估

## 技术选型指南

- **混合检索**：生产环境始终使用。查询时几乎没有额外开销。
- **重排序**：当 Recall@50 良好但 Recall@5 较差时使用。会增加 50-200ms 延迟。
- **HyDE**：当查询含糊或与文档词汇不一致时使用。会增加一次 LLM 调用。
- **父子片段**：当小片段缺乏上下文、大片段又稀释相关性时使用。
- **元数据过滤**：当语料有清晰类别（日期、来源类型、部门）时使用。
- **查询分解**：用于需要从多个文档获取信息的多跳问题。

## 常见错误

- BM25 与向量检索使用不同的片段集合（两者必须检索同一语料）
- 重排序的候选池过小（top-10 太少，应使用 top-50）
- 对每个查询都加 HyDE（仅在词汇不匹配是瓶颈时才有帮助）
- 不评估改动效果（每项技术前后都要测量 Recall@k）
- 在没有测量瓶颈所在之前就过度工程化流水线

## 评估流程

1. 准备 50 个以上带有已知答案片段的测试问题
2. 对每种检索方法测量 Recall@5 和 Recall@10
3. 对于检索成功的查询，测量生成答案的忠实度
4. 随语料增长每周跟踪指标
5. 在引入更多技术之前，先调查个别失败案例
