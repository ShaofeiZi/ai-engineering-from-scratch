# LLM 成本优化模式

当构建需要控制成本的 LLM 应用时，请应用此决策框架。

## 何时优化

**立即优化的条件：**
- 月度 LLM 支出超过 $500 或基础设施预算的 10%
- 面向消费者产品的每查询成本高于 $0.01
- 系统提示词超过 1,000 token 且每次请求都发送
- 超过 30% 的查询是重复或近似重复的
- 你正从 100 日活用户扩展到 10,000+ 日活用户

**暂不优化的条件：**
- 日活用户少于 100，且仍在验证产品市场契合度
- 月度支出低于 $100 且增长缓慢
- 你仍在迭代提示词设计（缓存会把提示词固定下来）

## 缓存策略选择

### 精确缓存

**适用条件：** temperature=0、相同提示词重复出现、需要确定性输出。

```python
key = sha256(json.dumps({"model": m, "messages": msgs, "temp": 0}))
```

- 实施成本：30 分钟
- 命中率：大多数应用 10-25%，FAQ 机器人 40-60%
- 延迟：<1ms（字典查找）
- 风险：底层数据变化时返回陈旧响应

**跳过条件：** temperature > 0、每次查询都唯一、需要实时数据。

### 语义缓存

**适用条件：** 用户用不同措辞问同一个问题、FAQ 密集型产品、客户支持。

- 实施成本：2-4 小时（embedding + 相似度 + 存储）
- 命中率：在精确缓存之上再增 15-35%
- 延迟：10-50ms（embedding + ANN 搜索）
- 风险：假阳性（对相似但不同的问题返回了错误的缓存答案）

**阈值建议：**
- 0.98+：非常保守，几乎没有假阳性，命中率较低
- 0.95：事实性问答的良好平衡点
- 0.90：激进，命中率较高但有答错的风险
- 0.85：仅适用于低风险场景（建议、自动补全）

**跳过条件：** 每次查询都有独特上下文（代码生成）、响应必须反映最新数据、查询空间无边界。

### 提供商提示词缓存

**适用条件：** 系统提示词 > 1,024 token（OpenAI）或模型特定的最小值、相同前缀被重复发送。

| 提供商 | 操作 | 节省 |
|----------|--------|---------|
| Anthropic | 在系统消息上添加 `cache_control: {"type": "ephemeral"}` | 缓存前缀节省 90%（扣除 25% 写入溢价后） |
| OpenAI | 无需操作（自动） | 缓存前缀节省 50% |
| Google | 使用 Context Caching API 并显式设置 TTL | 缓存上下文约节省 75% |

**跳过条件：** 系统提示词每次请求都变化、提示词低于最小长度。

## 模型路由规则

### 基于关键词（简单、快速）

```
simple:  <= 5 words OR matches FAQ keywords -> gpt-4o-mini ($0.15/$0.60)
medium:  general queries, summaries        -> claude-sonnet ($3/$15)
complex: "analyze", "compare", "debug"     -> gpt-4o ($2.50/$10)
```

- 实施成本：1 小时
- 准确率：70-80%
- 节省：模型成本的 40-60%

### 基于 embedding（更准确）

每个类别标注 50-100 条查询。通过最近邻对新查询分类。

- 实施成本：4-8 小时
- 准确率：85-92%
- 节省：模型成本的 50-70%
- 额外成本：分类 embedding 约 $0.02/1M token（可忽略）

### 基于机器学习（生产级）

在历史"查询/模型"配对上训练一个小型分类器（逻辑回归或小型 BERT）。

- 实施成本：1-2 周
- 准确率：90-95%
- 节省：模型成本的 60-75%
- 前提：需要来自生产流量的标注训练数据

## 限流配置

### 按层级的令牌桶参数

| 层级 | 桶大小 | 补充速率 | 最大 RPM | 日额度 |
|------|-------------|-------------|---------|-----------|
| Free | 50K tokens | 500/秒 | 10 | 50K |
| Pro | 500K tokens | 5K/秒 | 60 | 500K |
| Enterprise | 5M tokens | 50K/秒 | 300 | 5M |

### 实施清单

1. 将桶存储在 Redis 中（而非内存），适用于多实例应用
2. 使用原子操作（MULTI/EXEC）防止竞态条件
3. 在拒绝响应中返回 `Retry-After` 头
4. 将被拒绝的请求作为指标跟踪（拒绝率 >5% 说明层级限制过紧）
5. 实现优雅降级：先拒绝昂贵模型的请求，保留便宜模型的访问

## 预算控制

### 三阈值熔断器

| 阈值 | 动作 | 可恢复 |
|-----------|--------|------------|
| 月度预算的 70% | 记录告警，通过 Slack/PagerDuty 通知团队 | 是（自动） |
| 月度预算的 85% | 将所有流量路由到最便宜模型 | 是（自动，下一计费周期） |
| 月度预算的 95% | 仅返回缓存响应，拒绝新的 LLM 调用 | 是（手动重置或下一周期） |

### 按用户成本跟踪

跟踪每位用户的累计成本。标记超过中位数 10 倍的用户。常见原因：
- 合理的高级用户（提升其层级）
- 提示词注入循环（机器人发送自动化请求）
- 低效集成（客户端在每个错误上都重试）

## 成本跟踪字段

记录每次 API 调用，包含以下字段：

```json
{
  "timestamp": "2026-04-02T10:30:00Z",
  "model": "gpt-4o",
  "input_tokens": 1523,
  "output_tokens": 487,
  "cached_input_tokens": 1024,
  "latency_ms": 1847,
  "cost_usd": 0.006142,
  "user_id": "user_abc123",
  "cache_status": "partial_hit",
  "request_category": "customer_support",
  "complexity_class": "medium",
  "routed_from": "gpt-4o"

```

### 仪表盘关键指标

- **每查询成本**（P50、P95、P99）—— 按模型、按功能、按用户层级
- **缓存命中率** —— 精确缓存 vs 语义缓存、随时间变化的趋势
- **模型分布** —— 每个模型的流量占比、每个模型的成本
- **预算消耗速率** —— 当前支出 vs 当前速率下预测的月度支出
- **拒绝率** —— 被限流的请求占比，按层级

## 常见错误

| 错误 | 危害 | 修复 |
|---------|-------------|-----|
| 在 temperature > 0 时缓存 | 输出非确定，陈旧缓存会丧失多样性 | 只缓存 temp=0 调用，或接受缓存响应失去随机性 |
| 语义缓存阈值过低 | 对表面相似但不同的查询返回错误答案 | 从 0.95 起步，只有在测量假阳性率后才下调 |
| 无缓存失效 | 底层数据变化时响应变陈旧 | 设置 TTL（动态数据 1 小时、静态数据 24 小时），在数据更新时失效 |
| 将所有流量路由到最便宜模型 | 质量下降，用户察觉到 | 按复杂度路由，按层级测量质量，设置最低质量阈值 |
| 无按用户限制 | 一个滥用用户耗尽整个预算 | 始终实施按用户配额，即便额度很大 |
| 忽略输出 token | 每 token 输出成本是输入的 2-5 倍 | 合理设置 max_tokens、使用停止序列、压缩输出 |
| 提示词未稳定就缓存 | 缓存被旧提示词的响应填满 | 只在提示词定稿后启用缓存，提示词变更时刷新缓存 |
