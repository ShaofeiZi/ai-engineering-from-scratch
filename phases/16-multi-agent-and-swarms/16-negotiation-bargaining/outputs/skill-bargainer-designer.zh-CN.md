给定一个协商或任务市场场景（双边讨价还价、N 方拍卖、contract-net 任务分配），设计该协议。

需产出：

1. **机制。** 双边讨价还价、N 方出价拍卖、contract-net 广播还是多方联盟。指明博弈类型。
2. **报价生成器。** 确定性（Zeuthen 式让步、Rubinstein 均衡、简单线性方案）还是 LLM 提示生成。默认：确定性，除非报价必须是定性结构（提案、角色分配）。
3. **叙述层。** LLM 贡献什么：面向人类的框架、说服策略、人设。明确说明 LLM 不决定什么。
4. **私有与公开通道。** 推理轨迹如何与对手的上下文隔离。"私有草稿区" + "公开消息"作为两个字段。这依据 arXiv:2503.06416 是不可妥协的。
5. **轮次上限。** 双边最多 3-5 轮。无界不是选项；它会奖励从众行为并鼓励情绪化报价。
6. **保留价与 BATNA 纪律。** 双方必须知道自己的保留价。若对方试探，LLM 叙述者不得泄露。对每条外发消息验证此规则。
7. **成交率监控。** 该协议的预期基线成交率（引用协商基准中的数字：27%-89% 范围，取决于 LLM 角色）。回退预警阈值。
8. **升级路径。** 低于阈值的轮次、ZOPA 违约或对方违规，路由至调解智能体或人类。

硬性否决条件：

- 任何让 LLM 在无确定性退路的情况下计算数值报价的设计。arXiv:2402.15813 显示这会产生约 27% 的成交率。
- 任何没有独立私有和公开通道的设计。对手会读到你的推理。
- 任何无界轮次的设计。必定产生从众驱动的结果。
- 允许单个智能体同时持有买方和卖方状态的设计（角色扮演式讨价还价）。私有信息属性就是机制本身；合并角色会消除它。

拒绝规则：

- 若任务无数值收益（定性协商、合同条款），OG-Narrator 分解可能不适用。建议改用结构化提案 + 模式验证。
- 若用户无法实现独立草稿区（单次 LLM 调用架构），明确标记泄露风险并建议双调用架构。
- 若协商是对抗性的且对方可能说谎，建议使用调解智能体加可审计的日志报价。

输出：一份一页简报。以单句总结开头（"双边讨价还价：Zeuthen 报价生成器 + LLM 叙述者，5 轮上限，独立草稿区，成交率低于 85% 时预警。"），然后是上述八个部分。以一条示例消息结尾：对手看到的内容 vs 私有草稿区持有的内容。
