给定一个多智能体代码库或架构文档，审计其共享内存设计并标记内存投毒风险。

需产出：

1. **拓扑结构。** 是完整消息池、按主题分区的黑板、按智能体投影的视图，还是混合模式？指明数据结构类型（列表、字典、pandas DataFrame、向量存储、SQL 表）。估算稳态下写入者和读取者数量的粗略上限。
2. **来源溯源字段。** 每次写入时，条目是否记录：写入者 ID、时间戳、提示哈希或提示文本、工具调用轨迹、来源 URI 或工具名称？列出已有字段和缺失字段。
3. **更新模型。** 日志是仅追加的，还是写入者就地修改？若为就地修改，并发控制机制是什么（锁、乐观版本控制、无）？更正应为替代条目而非就地编辑——任何未遵循此做法的设计都应标记。
4. **验证器隔离。** 是否存在一个具有独立数据源访问权限的只读智能体？它能否写入主池（不应能）？其输出去往何处？
5. **投影模式。** 若设计使用投影（LangGraph reducers、黑板主题、角色限定视图），模式是否有文档记录？新智能体如何声明其消费的投影？
6. **投毒风险评分。** 在每个维度上打 1-5 分：[来源溯源完整性]、[替代优先于就地修改]、[验证器独立性]、[投影模式清晰度]。任一维度低于 3 分的系统将被标记。

硬性否决条件：

- 任何未标记缺失验证器的审计。一个不可写入、具有独立数据源访问权限的验证器是承重性缓解措施；没有它，所有其他缓解措施都只是装饰。
- 建议"增加更多测试"的审计。测试无法捕获内存投毒，因为投毒产生的是能通过测试的合理输出。
- 建议仅对内容做哈希作为唯一来源溯源的审计。哈希只能告诉你写了*什么*，不能告诉你*谁*写的或*来自哪里*。

拒绝规则：

- 若代码库将共享状态隐藏在外部服务（Redis、Postgres、向量数据库）中且无检查工具，声明审计无法在无生产读取权限下完成。
- 若系统智能体数量少于三个，注明内存投毒风险较低，但来源溯源仍是低成本的保险。
- 若系统使用内置状态管理的框架（LangGraph checkpointer、AutoGen pool），审计框架的保证而非重新推导。

输出：一份两页报告。以一句话总结开头（"共享状态是一个无来源溯源、无验证器的完整消息池——投毒风险高。"），然后是上述六个部分。以优先级行动列表结尾：三项改动，每项标注 [critical]、[should] 或 [nice-to-have]，并附估计实施时间。
