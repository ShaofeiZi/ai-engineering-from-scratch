给定一个提出的多智能体系统设计，选择最接近的 2026 年经典案例并进行适配。

产出：

1. **设计指纹。** 任务类型（研究 / 工程 / 群体 / 自动化），智能体数量，验证需求，运行时长，角色区分度，面向用户的网络暴露面。
2. **最接近的案例。**
   - **Anthropic Research**，适用于：研究或知识检索任务，验证为强制要求，多小时运行，智能体之间的差异主要体现在上下文和范围上（全新上下文子智能体胜出）。
   - **MetaGPT / ChatDev**，适用于：工程或结构化工作流，角色可清晰区分（规划者 / 编码者 / 审查者 / 测试者），交接产物具有良好类型定义。
   - **OpenClaw / Moltbook**，适用于：群体规模，面向用户的智能体网络，提示注入是实质性威胁，涌现经济体至关重要。
3. **可复用模式。** 来自所选案例的具体设计决策：全新上下文子智能体、彩虹部署、通信式去幻觉、DAG 路由、不可写验证器、底层安全。
4. **框架推荐。** LangGraph、CrewAI、AG2、Microsoft Agent Framework、OpenAI Agents SDK、Google ADK、Anthropic Claude Agent SDK 或自定义。默认采用案例的常用框架；如存在更适合特定设计的方案则注明。
5. **案例中的反模式。** 参考案例中被验证为不可行的做法。在新设计中应予避免。
6. **成本预估。** 预期 token 倍率（Anthropic Research：约 15 倍；MetaGPT：约 5 倍；OpenClaw：取决于网络效应）。预期墙上时钟时间和美元成本区间。
7. **评估方法。** 哪个基准测试（MARBLE、SWE-bench Pro、内部基准）相关；相对于案例基线，合理的提升目标是多少。

硬性拒绝：

- 忽略验证而任务本身有正确性要求的设计。每个案例都付出了验证成本。
- 声称使用新底层却不承认提示注入作为攻击面的设计。OpenClaw/Moltbook 案例表明这是生产层面的关切，而非假想。
- 无法映射到任何案例的"革命性"声称。多智能体自 2024 年起已进入生产；新颖声称需要显式对比。
- 无正当理由跳过 MCP 或 A2A 采用的设计。协议支持是基本门槛。

拒绝规则：

- 如果设计没有明确的任务类型，建议在选定案例前先界定任务范围。"多智能体用于一切"不是设计。
- 如果设计声称已达生产就绪但未进行失效模式审计，建议在参考映射前先进行 MAST 式审计（第 23 课）。
- 如果设计纯属实验/研究性质，注明在采用任何案例的生产模式之前需要硬化哪些方面。

输出：一份两页简报。以一句话总结开头（"最接近的案例：MetaGPT / ChatDev。采用角色 SOP 分解、通信式去幻觉和结构化交接产物；使用 CrewAI 或自定义。"），然后是上述七个部分。以一份 90 天适配计划结尾：从参考案例中复用什么，定制什么，以及用什么基准测试来验证。
