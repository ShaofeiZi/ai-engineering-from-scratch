给定一个多智能体系统和采样的执行追踪，运行失败模式审计。

产出：

1. **样本构建。** 来自生产的至少 200 条追踪，跨任务类型和时间窗口均匀采样。记录采样方法和偏差风险。
2. **分类标注。** 对每条追踪，标记 `success | failure`。对于失败，分配一个 MAST 类别（spec / coord / verify），并在适用时附加一个或多个 Groupthink 家族标签（monoculture / conformity / tom / mixed-motive / cascade）。
3. **分布表。** 按 MAST 类别和 Groupthink 标签的计数和百分比。与 Cemri 2025 的参考分布（41.77 / 36.94 / 21.30）比较。严重偏离参考分布的系统通常存在特定的薄弱层。
4. **Top 失败模式。** 识别 3 个最频繁的具体模式（如"两个智能体都在审查"）。记录复现步骤。
5. **缓解措施排序。** 对每个 Top 模式，从标准库中提出缓解措施：显式角色契约、版本化共享状态、独立验证器、熔断器、检测-诊断-验证（STRATUS）三联体。按该模式频率下的预期失败减少量排序。
6. **静默失败风险。** 多少失败产生看似合理但错误的输出 vs 明显报错？静默率驱动验证层的投入。
7. **慢失败代理指标。** 推荐 2-3 个能在漂移变成明显错误之前暴露它的实时指标：一致率、重试率、输出长度分布、智能体间编辑距离。

硬性拒绝：

- 没有随机或分层样本的审计。手工挑选的失败过度代表戏剧性案例，遗漏慢失败漂移。
- 没有基线测量的缓解推荐。"添加验证器"在不知道当前失败率时毫无意义。
- 忽略 MAST 未知事件。如果一条追踪不属于任何类别，分类法不完整；提出扩展而非强行归类。
- 声称季度审计足够而没有运行中的慢失败监控。季度审计会遗漏审计之间的漂移。

拒绝规则：

- 如果追踪缺少每个智能体的归因（谁写了什么、谁读了什么），审计无法区分协调失败和角色冲突。建议在重新审计前添加结构化的每智能体日志。
- 如果系统总失败追踪少于 50 条，样本太小，无法产生分布估计。建议延长观察窗口。
- 如果追踪包含 PII，分析前先脱敏。

输出：一份三页报告。以一句话摘要开头（"41% spec 失败，12% 协调，39% 验证缺口，8% 未知；首要模式是双审查者冲突；ROI 最高的缓解措施是显式角色契约。"），然后是上述七个部分。以优先级行动列表结尾：三项缓解措施及估算的实施成本和预期失败率降低。
