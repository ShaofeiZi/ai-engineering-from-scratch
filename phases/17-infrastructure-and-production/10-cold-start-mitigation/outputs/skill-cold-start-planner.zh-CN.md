给定模型规模、SLA（TTFT P99）、流量形态（平稳 vs 突发）和预算姿态，产出一份冷启动缓解计划。

产出内容：

1. 冷启动预算。分解原始冷启动路径（节点分配、镜像拉取、权重加载到 HBM、引擎初始化、首次前向）。使用 2026 年针对所述模型规模的标称秒数。
2. 层级选择。选择使总时间降至 SLA 以下所需的最少层级数：预置镜像（L1）、模型流式加载（L2）、GPU 快照（L3）、预热池（L4）、分层加载（L5）。针对每层所攻击的具体阶段进行论证。
3. 预热池容量。声明主路径的 `min_workers`。如果 SLA 为 70B+ 模型 TTFT P99 < 60s，则无论成本如何都必须设置预热池。
4. 成本估算。所选预热池的月度 GPU 成本及每日预期冷启动次数。
5. 尾部策略。全新副本上的第一个用户会怎样——是排队到预热副本，还是承受冷启动代价？命名一个具体策略（例如"10 秒内将首个请求路由到任意预热副本；否则降级为冷启动"）。
6. 故障模式。如果预热副本在会话中途死亡会怎样。恢复是自动的（实时迁移），还是下一次请求时冷启动？

硬性拒绝条件：
- 在未计算月度成本的情况下提出"加预热池就行"。
- 声称某缓解措施有效而未指明其攻击的具体阶段（例如"用 Bottlerocket"而不说明它消除了 180s 的镜像拉取）。
- 忽视 GPU 快照的 GPU 拓扑约束——如果平台迁移了 SKU，快照将失效。

拒绝规则：
- 如果 SLA 为全新 70B 冷启动 TTFT P99 < 5s 且无预热池，拒绝——在 2026 年基础设施速度下数学上不可能实现。
- 如果预算不允许预热池但 SLA 要求低于 30s 的冷启动，指明平台特定的修复方案（Modal GPU 快照、Baseten 预热），并拒绝在没有该方案的其他平台上承诺该 SLA。
- 如果运维方要求对突发流量的 70B 模型缩容至零且承诺 SLA，拒绝——没有快照或预热池，数学不成立。

输出：一份单页计划，列出各阶段、各层、`min_workers`、月度成本、尾部策略、故障模式。以需要告警的单个指标收尾：最近滚动一小时的 P99 冷启动时长。
