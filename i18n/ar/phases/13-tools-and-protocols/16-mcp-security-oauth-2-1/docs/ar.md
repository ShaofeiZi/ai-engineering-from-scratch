# MCP الإذن: CIMD، إلتزام المصدر PKCE، و " Step-Up "

> جهاز التحكم عن بعد MCP الطلب غير مصدر للدولة، لكن تفويضه ليس مجهولاً. ربط كل إثباتات إلى المصدر الذي صنعها وكل رمز إلى الموارد التي تتلقىها.

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 13 · 09 (transports), Phase 13 · 15 (security)
**Time:** ~90 minutes

## أهداف التعلم

- اكتشاف خادمات الائتمان من خلال البيانات المعدنية الموارد المحمية.
- يفضل العميل ID وثائق البيانات المعدنية حول تسجيل العميل الديناميكي القديم.
- إعلان الصواب `application_type` عندما DCR مسار التوافق لا مفر منه.
- تأكييد رد الإذن `iss` وتعزل الإثباتات حسب المصدر.
- الاستخدام PKCEمؤشرات الموارد، وصحيحة الجمهور، ومناطق متزايدة.
- إرسال مصرح به MCP طلبات 2026-07-28 بدون جلسات بروتوكول

## المشكلة

جهاز التحكم عن بعد MCP قد يقرأ الخادم السجلات الخاصة، أو يكتب أنظمة خارجية، أو يؤدي إلى عمل مكلف. يخبر المصادقة من قدم شهادة اعتماد. يجب على الائتمان أيضا الإجابة:

- أي خادم تصريح أصدر هذه الإصدارات؟
- الذي MCP الموارد هي رمز؟
- أي عميل وإعادة توجيه URI أكملت التدفق؟
- أي عمليات المستخدم قد وافق عليها؟
- هل هذا الطلب الدقيق لا يزال يناسب هذا الموافقة؟

ملف تفويض 2026-07-28 يُصلب تسجيل العملاء ومعالجة المصدر. ID وثائق البيانات المعدنية، يمنع تسجيل العميل الديناميكي، يتطلب الحق `application_type` على DCR، يصدق RFC 9207 ردات المصدر، ويحظر إعادة استخدام المراجع بين المصدرين.

هذه القواعد تكملة الصلة الفارغة. `Mcp-Session-Id`.

## المفهوم

### تعرف على الأدوار الثلاثة

- **MCP العميل:** يرسل طلبات نيابة عن صاحب الموارد.
- **MCP خادم الموارد:** يقبل رمز الوصول و يخدم MCP نقطة النهاية
- **خادم الإذن:** يثبت أصحاب الموارد، ويجمع الموافقة، ويصدر رموز.

يمكن تشغيل خادم الموارد وخادم الترخيص معاً، ولكن إبقاء تحديداتهم ومسؤوليات التحقق من التحقق منفصلة.

### تطبق الموافقة على HTTP

المُسَمِع MCP تطبق مواصفات الترخيص على HTTP-based النقل. خادم استوديو محلي يعمل تحت حدود ثقة العملية والنظام التشغيلي. لا تضيف متصفح مزيف OAuth تدفق إلى الاستديو فقط للتناظر

للشاشة عن بعد HTTP، أرسل الجهاز المحمل في `Authorization` الرأس على كل طلب. URL.

### ابدأ بمعلومات البيانات المعدنية المستخدمة في الموارد المحمية

خادم الموارد ينشر RFC 9728 البيانات المعدنية:

```json
{
  "resource": "https://notes.example.com/mcp",
  "authorization_servers": ["https://auth.example.com"],
  "scopes_supported": ["notes:delete", "notes:read", "notes:write"]
}
```

العميل يبدأ من MCP الموارد URL، يحصل على هذا الوثيقة، يختار خادم الإذن الإعلانية، ومن ثم يحصل على خادم OAuth أو OpenID ربط البيانات المعدنية

الحفاظ على مسار الموارد عند بناء RFC 9728 well-known URL. بالنسبة للموارد `https://notes.example.com/mcp`، هذا الدروس يستخدم `https://notes.example.com/.well-known/oauth-protected-resource/mcp`- أترك `/mcp` يمكن للاستحقاق اختيار البيانات المعدنية لمصدر محمي مختلف من نفس المنشأ.

لا تخمين خادم الائتمان من اسم مضيف. لا تتبع مستثمرًا اكتشف من جسم خطأ غير معتمد. احتفظ بسياسة يود العميل الثقة في مستثمرين.

### التحقق من بيانات المستخدم المعتمدة

يجب أن تكشف البيانات الوصفية نقاط النهاية والتحكمات المدعومة:

```json
{
  "issuer": "https://auth.example.com",
  "authorization_endpoint": "https://auth.example.com/authorize",
  "token_endpoint": "https://auth.example.com/token",
  "code_challenge_methods_supported": ["S256"],
  "authorization_response_iss_parameter_supported": true,
  "client_id_metadata_document_supported": true
}
```

تطلب S256 لـ PKCE. سجل السلسلة المصدقة بالضبط، هذه القيمة المحددة تصبح مفتاح التسجيل وتخزين الرمز.

### اتبع أولوية التسجيل

استخدم معلومات العميل المسجلة مسبقاً عندما يكون لدى العميل علاقة صريحة بالفعل مع المصدر المختار. وإلا تفضل العميل ID المعلومات المعدنية الوثائق عندما يعلن خادم الإذن عن الدعم. DCR فقط كخلف التوافق القديم، ثم استدعاء معلومات العميل إذا لم تكن هناك أي من هذه الآليات متاحة.

### يفضل العميل ID وثائق البيانات المعدنية

عميل ID يمنح المستند البيانات المعدنية خادم الإذن HTTPS URL وهو هو هويت العميل وموقع بياناته المعدنية:

```json
{
  "client_id": "https://client.example.com/oauth/metadata.json",
  "client_name": "Notes desktop client",
  "application_type": "native",
  "redirect_uris": ["http://127.0.0.1:8765/callback"],
  "grant_types": ["authorization_code"],
  "response_types": ["code"]
}
```

خادم الإذن يحصل على وثيقة ويمتحرها `client_id` يجب أن يكون HTTPS URL مع مسار، والقيمة داخل الوثيقة يجب أن تكون مساوية لذلك URL بالضبط. الحقول المطلوبة في الوثيقة هي `client_id`, `client_name`و `redirect_uris`. `application_type` يظهر في هذا المثال ولكن ليس CIMD الاحتياج. استخدامها الإلزامي الجديد هو على وجه التحديد DCR الطريق

تعامل الحصول على الوثيقة ك SSRF-sensitive عملية: حل وتؤكيد الوجهة، رفض الخلفية، والخاصة، والترابط المحلي، وغيرها من العناوين غير المسموح بها، التحقق من جديد بعد إعادة التوجيهات، DNS تغييرات، الحد من إعادة التوجيهات، البايتات، والوقت، تتطلب JSON، و التخزين فقط وفقا للتحقق HTTP التحكمات في الاحتفاظ `client_name` و غيرها من حقل العرض كنص غير موثوق به.

CIMD يزيل الحاجة إلى وضع معرف ديناميكي جديد لكل اتصال أول. URI التحقق من المصادقة، سياسة المصدر، أو موافقة المستخدم.

### DCR هو مسار التوافق

لا يزال تسجيل العميل الديناميكي متاحًا لمستخدمات الإذن القديمة ، لكنه قد انتهى من الصلاحية بالنسبة للخادمات الجديدة MCP التنفيذ

عند استخدامها DCR، إعلان `application_type`:

```json
{
  "client_name": "Notes desktop client",
  "application_type": "native",
  "redirect_uris": ["http://127.0.0.1:8765/callback"],
  "grant_types": ["authorization_code"],
  "response_types": ["code"]
```

### إرشادات الوصف للمصدر

تخزين مواد التسجيل التي يكتبها المصدر تحت عنوان المصدر الدقيق:

```text
issuer_credentials[issuer] = pre_registered_or_dcr_client
tokens[(issuer, resource)] = access_token
```

إذا كان اكتشاف الموارد المحمية يتغير من `https://auth-one.example` إلى `https://auth-two.example`لا ترسل أبداً سر العميل الأول DCR هويت العميل، رمز الوصول للتسجيل، رمز التجديد، أو رمز الوصول إلى الثاني. DCR يجب على العملاء استخدام إثباتات صادرة عن المصدر الجديد.

A CIMD هو مختلف لأنه هو مضيف ذاتي HTTPS URLلا تصريحات مصوّرة من قبل خادم تصريح CIMD URL هو قابل للنقل: مصدر جديد موثوق به يحضر ويمتحن الوثيقة دون DCR إعادة التسجيل. استجابات الموافقة والرموز لا تزال معتمدة وتخزن تحت المصدر الجديد.

### رمز الترخيص مع PKCE

التدفق التفاعلي هو:

1. توليد طاقة عالية `code_verifier`.
2. استنتاج S256 `code_challenge`.
3. أرسل طلب التأذن مع الدقة `client_id`, `redirect_uri`, `scope`, `code_challenge`و `resource`.
4. تلقي رد على الموافقة يحتوي على `code` وعندما يتم توفيرها `iss`.
5. التحقق من الصلاحية `iss` ضد المصدر المسجل الدقيق قبل استخدام أي حقل استجابة.
6. تبادل الرمز مع `code_verifier`، نفس إعادة التوجيه URI، و نفس `resource`.
7. تخزين الرمز الناتج تحت `(issuer, resource)`.

المُسَمِع `resource` المعلم من RFC 8707 يظهر في كل من الطلبات المفروضة والرمز. MCP الخادم URI.

### التحقق من الصلاحية `iss` بالضبط

RFC 9207 يمنع استجابة تصريح من أحد المصدرين من الخلط بين استجابة من آخر.

متى `iss` إذا كان موجوداً، قم بمقارنةها مع المصدر المسجل دون طيّة الحالة، وتغييرات التقطيعات التالية، وإزالة منفذ افتراضي، أو تطبيع تشفير النسبة المئوية. في حالة عدم التطابق، لا تتصرف على الرمز أو حتى تعرض تفاصيل الخطأ التي يتحكم بها المهاجم من تلك الاستجابة.

خادم تصريح يتضمن `iss` الإعلانات `authorization_response_iss_parameter_supported: true`العملاء الحاليون لا يزالون يصدقون هدية `iss` حتى عندما يفتقد هذا الإعلان

### المشاهدين المثبتين في MCP الخادم

يقبل خادم الموارد فقط الرموز المصدرة لنفسه:

```text
token.issuer == configured_authorization_server
token.audience == canonical_mcp_resource
```

الـ 401 تتلقى رموز غير صالحة أو انتهت صلاحيتها أو أصدرها بشكل خاطئ أو أصدر الجمهور بشكل خاطئ MCP لا يجوز للخادم قبول أو نقل رمز يُعدّ لخدمة أخرى.

### طلب أصغر نطاق للشحن

ابدأ من النطاق المطلوب الآن. إذا كانت أداة لاحقة تتطلب المزيد، يعود الخادم 403 مع تحد النطاق المعتمد:

```text
WWW-Authenticate: Bearer error="insufficient_scope",
  scope="notes:delete",
  resource_metadata="https://notes.example.com/.well-known/oauth-protected-resource/mcp"
```

يقوم العميل بتفسير الإذن الجديد، ويحصل على موافقة، ويقوم بتدفق إذن جديد مع مجموعة النطاق المشترك، ويعيد محاولة MCP طلب مع طلب جديد JSON-RPC هوية

لا نفترض أن النطاق المتحدى هو مجموعة فرعية من `scopes_supported`التحدي هو المعتمد للعملية الحالية.

### التأذن والشخصية MCP السلك

دعوة أداة مصرح بها لا تزال تحتوي على غلاف الطلبات الكاملة الحالية:

```text
POST /mcp
Authorization: Bearer <access-token>
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: notes.delete
```

```json
{
  "jsonrpc": "2.0",
  "id": 12,
  "method": "tools/call",
  "params": {
    "name": "notes.delete",
    "arguments": {"id": "note-7"},
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": {
        "name": "oauth-lesson-client",
        "version": "1.0.0"
      }
    }
  }
}
```

الوهم يسمح للمدير، البيانات المطلوبة تتفاوض على سلوك البروتوكول، ولا أحد يبدل الآخر.

تأكيد الأسلاك في ترتيب ثابت: JSON-RPC وتعد أنواع البيانات المعدنية، والرأس والجسم المساواة، ثم دعم البروتوكول. يعود إضطراب التوجيه أو نسخة-رأس HTTP 400 with `-32020`إذا اتفق الرأس والجسم على نسخة غير مدعومة، أعيد HTTP 400 with `-32022` و `data` بالضبط `{"supported":["2026-07-28"],"requested":"<actual>"}`. طريقة مجهولة تعود HTTP 404 with `-32601`.

كل خطأ في الطلب، بما في ذلك 401 رمز غير صالحة و 403 نطاق غير كاف، هو JSON-RPC غلاف الخطأ مع الطلب الأصلي `id`. معلومات الاسترداد المهيكلة تنتمي إلى خطأ اختياري `data`; `WWW-Authenticate` يبقى HTTP عنوان الاستجابة. `id`، لذلك لا تتلقى JSON-RPC الهيئة. HTTP الإخطار يعود 202 مع جسم فارغ.

الخادم ينفذ `server/discover` وتعلن عن الأدوات، لذلك فإنها تنفيذ أيضا الإجبارية `tools/list` طريقة. وصف الأدوات لديها أسماء مستقرة، وصف، وجذر الكائن `inputSchema` القيم. القائمة هي تحديدية وتعطي `resultType`، بيانات المستخدم المحدودة `ttlMs`و `cacheScope`. يمكن الحصول على قائمة أدوات اكتشافية ومستقلة عن المستخدم قبل الحصول على الموافقة. تطبق السياسة العادية والاحتفاظ بحفظ الاحتياطي الخاص إذا كان أي منها يختلف حسب الرقم.

### لا يوجد رمز عبر

(إنجليزية) MCP لا يجب على الخادم إرسال رسائل العميل MCP رمز الوصول إلى متصفح أسفل API. الحصول على رمز منفصل في التيار التالي مع الجمهور المناسب أو استخدام تصميم صريح لتبادل الرمز. يؤدي التحقق من المصادقة الجمهور فقط عندما ترفض الخدمات الرمز المختص لشخص آخر.

### رموز التجديد

إعادة إصدار الرموز اختياريًا. عند إصدارها، تخزينها سرية وتقوم بتفريغها حسب المصدر والموارد. لا نفترض وجودها. قم بتدويرها عندما يدعم خادم الإذن الدوران وتكتشف إعادة استخدام القيم غير صالحة.

## استخدمها

خريطة كائنات المحاكاة إلى مكونات الإنتاج:

- `ResourceServer.protected_resource_metadata` يصبح RFC 9728 endpoint.
- `AuthorizationServer.metadata` يصبح RFC 8414 or OpenID ربط الاكتشاف
- `Client.enroll` يصبح CIMD قرار بالإضافة إلى صريح DCR فرع التوافق
- وثائق اعتماد العميل المحددة من المصدر `tokens_by_issuer_resource` تصبح سجلات مشفرة. CIMD URL يمكن أن تظل قابلة للنقل بينما تظل نتائج تصريحها مرتبطة بالمصدر.
- `ResourceServer.handle` يصبح البرمجيات المتوسطة التي تؤكد الحالي MCP العناوين، والرموز، ومدى الأدوات قبل إرسال مع الحفاظ على كل خطأ الطلب في المطابقة JSON-RPC غلاف

## التمارين

1. إضافة دوران رمز التجديد ورفض إعادة استخدام رمز التجديد السابق.
2. إضافة قائمة الموافقات للمصدر عند تغيير المصدر، إعادة استخدام فقط جهاز محمول CIMD URL- رفض جميع الوثائق والرموز التي تم تصنيفها من قبل من قبل المصدر.
3. إضافة انتهاء الصلاحية إلى رموز الترخيصات وتأكيد فشل التبادل المتأخر.
4. قم ببناء خيار عميل الويب مع جهاز التحكم عن بعد HTTPS إعادة توجيه وتقارن DCR البيانات المعدنية إلى العميل الأصلي

| `iss` | RFC 9207 تحديد المصدر الذي استجاب للموافقة |
| مؤشر الموارد | RFC 8707 المعلم الذي يربط طلب رمزية إلى MCP الموارد |
| الجمهور | الموارد التي تكون رمزية صالحة لها |
| - إضافة | الإصدار الجديد للموافقة والرموز لإجراء نطاق إضافي للعملية الحالية |
| الإثباتات المرتبطة بالمصدر | سجلات التسجيل والرموز المعزولة عن طريق مستعرض خادم الموافقة الدقيقة |
