# MCP النقل: الاستديو و البث بدون جنسية HTTP

> الحوافز النقلية MCP الرسائل. لا توفر حالة البروتوكول المفقودة. `2026-07-28`, الاستديو المحلي والبث عن بعد HTTP كلاهما يحمل طلبات تصفية ذاتية.

**Type:** Learn
**Languages:** Python
**Prerequisites:** Phase 13, Lessons 07 and 08
**Time:** ~65 minutes

## أهداف التعلم

- اختر استوديو للعمليات الاطفال المحلية و Streamable HTTP للخدمات الشبكة.
- تنفيذ نقطة نهاية واحدة الحديثة POST-only يمكن تشغيلها HTTP العقد
- مرآة وتؤكيد MCP الإصدار، والطريقة، والأسماء ضد JSON-RPC الجسم
- التسليم حسب الطلب SSE ويعيشون طويلاً `subscriptions/listen` التيارات بشكل صحيح.
- الهجرة القائمة على جلسة وتراثها HTTP+SSE التنفيذات دون تقديم السلوك المتقليد على أنه حديث

## المشكلة

السابقة قابل للتسجيل HTTP الإصلاحات مزج من مفاوضات البروتوكول مع الاتصال وسلوك الجلسة. `Mcp-Session-Id`، كشف شخص مستقل GET التيار، تقبل DELETE لإنهاء الجلسة، والإستئناف SSE مع `Last-Event-ID`.

MCP `2026-07-28` كل طلب يمكن أن يصل على أي عامل صحي لأن نسخة بروتوكولها وقدرات العميل تتحرك في جسم الطلب. HTTP العناوين تعكس الحقول المحددة للتوجيه والسياسة، ولكن الخادم يؤكد تلك العناوين ضد الجسم قبل تنفيذها.

النتيجة أسهل في الحجم وأسهل في التفكير حول. وهذا يعني أيضا أن خادم يعلّم النقل 2025 كما الحالية يعلّم النموذج الخاطئ والأمن.

## المفهوم

### الاستديو

التماس الاستديو هو لعملية فرعية تم إطلاقها من قبل العميل:

- العميل يكتب واحد UTF-8 JSON-RPC رسالة على الخط إلى ستدين
- الخادم يكتب واحد UTF-8 JSON-RPC رسالة على كل سطر إلى Stdout.
- الخادم يكتب التشخيصات إلى ستدر
- الخادم يغادر فوراً على stdin EOF.
- كل طلب حديث يحمل إصدار و قدرات العميل في `params._meta`.

قد تكون العملية صالحة للعديد من المكالمات، ولكنها ليست جلسة بروتوكول حديثة. إذا خرجت بشكل غير متوقع، فإن الطلبات أثناء الرحلة تضيع. إعادة تشغيل العملية وإعادة اكتشافها وإعادة إدراجها وإعادة فتح الاشتراكات، وإعادة محاولة العمليات الآمنة مع هويات الطلبات الجديدة.

### يمكن تشغيلها HTTP في 2026-07-28

خادم حديث يُعرض واحد MCP نقطة نهاية مثل: `/mcp`، الذي يقبل POST.

كلّ شخص JSON-RPC طلب أو إخطار جديد HTTP POST. الجسم يحتوي على واحد JSON-RPC الرسالة العملاء لا يرسلون JSON-RPC ردود على الخادم

لطلب، يعيد الخادم إما:

- `Content-Type: application/json` مع واحد JSON-RPC الاستجابة؛ أو
- `Content-Type: text/event-stream` مع الإخطارات المتعلقة بهذا الطلب، تليها الإخطار النهائي JSON-RPC رد فعل

بالنسبة للإخطار المقبول، يعيد الخادم `202 Accepted` بدون جثة

يعلن العملاء عن كلا النوعين من الاستجابة:

```http
Accept: application/json, text/event-stream
```

### POST-only الوسائل POST-only

المباشرة الحديثة HTTP لا يوجد لها نفسها GET التيار و لا DELETE نقطة نهاية الجلسة

- `GET /mcp` العائدات `405 Method Not Allowed`.
- `DELETE /mcp` العائدات `405 Method Not Allowed`.
- `Mcp-Session-Id` يتم تجاهلها ولا يتم إختراعها أو التردد عليها
- `Last-Event-ID` يتم تجاهلها لأن التيارات الحديثة لا يمكن إعادة تشغيلها

إذا توقف تدفق الطلب الذي تمت طياره قبل استجابته النهائية، فقد العميل طلب الطيران. JSON-RPC id عندما يكون محاولة إعادة التشغيل آمنة. لا يجب أن تحاول استئناف التيار.

### التحقق من المصدر

الخوادم تؤكد `Origin` على الاتصالات الداخلية لمنع DNS إعادة التزامن. إذا كان العنوان موجوداً وليس مسموحاً صراحةً به، أعد `403 Forbidden`. العميل غير المتصفح قد ينسحب `Origin`، كما تسمح بها قواعد النقل الرسمية.

يجب أن يربط الخوادم المحلية `127.0.0.1`لا توجد كل واجهة. خدمات الشبكة لا تزال تحتاج إلى التوثيق والتصريح على كل طلب. التحقق من المصدر ليس التوثيق.

استخدم مطابقة المنشأ الدقيقة بعد التكوين القنوني. `origin.startswith("https://trusted.example")` غير آمنة لأنها تستطيع قبول الإضافات التي يسيطر عليها المهاجم

### مطلوب HTTP رؤوس البيانات المعدنية

كل عصرية POST يتضمن الطلب:

```http
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: notes_search
```

قواعد العنوان:

- `MCP-Protocol-Version` مطلوب ويجب أن يكون مساوياً `params._meta.io.modelcontextprotocol/protocolVersion`.
- `Mcp-Method` مطلوب ويجب أن يكون مساوياً JSON-RPC `method`.
- `Mcp-Name` مطلوبة `tools/call`, `resources/read`و `prompts/get`.
- `Mcp-Name` متساوية `params.name`أو `params.uri` لـ `resources/read`.
- قيم العناوين حساسة للقضية على الرغم من أن أسماء العناوين غير حساسة للقضية.

غير آمن أو غير آمنASCII `Mcp-Name` القيم تستخدم بالضبط UTF-8 Base64 الحارس:

```text
=?base64?{Base64EncodedValue}?=
```

الخادم يقرر هذه القيمة قبل مقارنتها مع الجسم

العناوين المرئية المفقودة أو غير المتكاملة أو غير المتكاملة تعود HTTP `400` مع JSON-RPC الرمز `-32020`إذا كان الرأس والجسم يتفقون على نسخة لا يدعمها الخادم، أعيد HTTP `400` مع `-32022` و بيانات الخطأ الدقيقة مثل `{"supported":["2026-07-28"],"requested":"2027-01-01"}`.

طريقة حديثة غير معروفة تعود HTTP `404` مع JSON-RPC `-32601`- المُتَعَدِّدُ JSON-RPC الجسم مهم لأن العميل من العصر المزدوج يستخدمها لتمييز خطأ حديث من خطأ نهاية إرث.

### المدى المطلوب SSE

الخادم قد يختار SSE في حالة طلب طويل الأمد:

```text
POST tools/call id=41
  <- notifications/progress related to id=41
  <- notifications/progress related to id=41
  <- JSON-RPC response id=41
stream closes
```

لا يجوز للخادم إرسال مستقل JSON-RPC تُستخدم نتائج طلب رحلة متعددة. إغلاق تيار الاستجابة يلغي ذلك الطلب.

لا تضيف SSE هويات الحدث لإعادة عرضها `Last-Event-ID` لا يُعتبر إعادة الإجراء جزءاً من الإصلاح الحديث.

### تغييرات طويلة الأمد تستخدم الاشتراكات/ الاستماع

استخدام طلب مفتوح من قبل العميل ، وليس بمفرده GET:

```json
{
  "jsonrpc": "2.0",
  "id": "listen-1",
  "method": "subscriptions/listen",
  "params": {
    "notifications": {
      "toolsListChanged": true,
      "resourceSubscriptions": ["notes://note-1"]
    },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": {
        "name": "course-client",
        "version": "1.0.0"
      }
    }
  }
}
```

المُسَمِع POST رد فعل طويل الأمد SSE الإرسال الأول هو `notifications/subscriptions/acknowledged`- الإقرار، كل إشعار عن التغيير، والنتيجة النهائية `io.modelcontextprotocol/subscriptionId` في `_meta`, يساوي اسم طلب الاستماع . قد يقوم الخادم بإصدار SSE التعليقات كحافظ على الأضواء. عندما ينخفض التيار، يقوم العميل بإعادة إصدار `subscriptions/listen` مع هوية طلب جديدة وإعادة تصحيح البيانات المتأثرة.

`resources/subscribe` و `resources/unsubscribe` لا تستخدمها في اتصال حديث

### حالة الطلب الصريحة

إزالة جلسات البروتوكول لا يمنع تدفقات العمل مع حالة. قد يقوم الخادم بتصوير مسدس حالة غير شفافة ويرجع إليه كنتيجة أداة طبيعية. يمر العميل بهذه المسدس كحجة صريحة في مكالمات لاحقة.

ربط الجهازات المقبلة بالصيغة الرئيسية الموثقة، وجعلها غير قابلة للاختبار، وتجاوز صلاحيتها، وافعل كل استخدام مرخصًا. وهذا يجعل الحالة مرئية في طبقة التطبيق بدلاً من إخفائها في صلة النقل.

الفشل الناجم عن حالة النسخة الخفية هو ميكانيكي:

1. الطلب A يصل إلى النسخة 1 و يخلق مسودة في ذاكرة تلك العملية.
2. لا يعود الرد على مسودة التعامل لأن التنفيذ يفترض أن الاتصال يحدد المسودة.
3. الطلب ب هو طازج POST و يصل إلى النسخة الثانية
4. النسخة 2 لديها بيانات بروتوكول صالحة ولكن لا طريقة لإسم أو تحميل المسودة، لذلك تتعطل سير العمل أو تقرأ الكائن المحلي الخطأ.
5. يبدو أن التوجيهات اللصقية تصحيح الأعراض حتى إعادة البدء أو التنفيذ أو إعادة التوقيع أو فشل التنفيذ يقل الطلب التالي.

الحدود الصحيحة لها جزءان يظل السياق البروتوكول في كل طلب. حالة التطبيق الدائم يعيش في متجر مشترك تحت المقبض المعدل الخادم أعيد إلى العميل. المكالمة التالية توفر المعاملة، أي نسخة تحميل نفس السجل، والإذن يربط السجل إلى المدير الموثق والمستأجر. قد تكون ذاكرة النسخة مخزنة لسجل، ولكنها لا يمكن أن تكون النسخة الوحيدة المطلوبة للصواب.

اختر آلية الحالة حسب الحياة. المتغيرات المحلية الطلب يمكن أن تعمل على اتصال واحد. MRTR الاستمرار يمكن استخدام حماية السلامة `requestState`. يُحتاج مسودة أو مهمة دائمة إلى مسدس صريح بالإضافة إلى استمرار مشترك، انتهاء الصلاحية، مراقبة التزامن، والفائدة. MCP جلسة البروتوكول

### HTTP التوافق بين العصور المزدوجة

العميل الذي يدعم الخوادم الحديثة والإرث يحاول POST أولاً، إذا استلمت HTTP `400`, `404`أو `405`، فهي تفتيش الجثة:

- معترف به الحديث JSON-RPC خطأ يثبت أن الخادم حديث. تصحيح الطلب أو حاول مرة أخرى نسخة إعلانية. لا تخفض الترتيب.
- الجسم الفارغ أو رد غير معروف قد يشير إلى تراث HTTP+SSE فقط بعد ذلك حاول القديم GET نقطة نهاية وتوقع تراثها `endpoint` الحدث

يمكن للخادم دعم كلا العصور أثناء الهجرة عن طريق توجيه البيانات المعدنية الحديثة إلى POST-only تنفيذ وتحفظ نقاط نهاية سابقة منفصلة للعملاء القديمين. GET, DELETE، اسم الجلسة ، أو سلوك التراجع كجزء من `2026-07-28`.

```figure
tp-transport-handshake
```

## استخدمها

`code/main.py` يطبق محرك تدفق حديث HTTP الخادم مع Python المكتبة القياسية. إنها تؤكد الأصل والعناوين المرئية، تتجاهل عناوين جلسات إزالة، تعود JSON للدعوات العادية، ويعرض `subscriptions/listen` SSE -تدفق

```bash
cd code
python3 main.py --probe
python3 -m unittest discover tests -v
```

-تحققات الصوت:

- يتم رفض المصل غير صالح؛
- الاكتشاف الناجح دون معرف جلسة
- `Mcp-Session-Id` و `Last-Event-ID` يتم تجاهلها.
- عودة عدم مطابقة العنوان `-32020`;
- إرجاع الإصدار غير المدعوم `-32022` مع دقة `supported` و `requested` البيانات
- إعلانات غير معرفية مقبولة HTTP `202` بدون جثة
- GET و DELETE العودة `405`;
- `subscriptions/listen` هو POST تدفق الاستجابة الذي يحمل الإقرار والإخطارات والنتيجة النهائية هويته الاشتراكية.

## التمارين

1. إزالة `Mcp-Method` من POST. تأكيد HTTP `400` وخطأ `-32020`.
2. إرسال نسخة مُطابقة من الرأس والجسم `2027-01-01`تأكّد HTTP `400`خطأ `-32022`و البيانات الدقيقة `{"supported":["2026-07-28"],"requested":"2027-01-01"}`.
3. أرسل Base64 المراقب `Mcp-Name` لغيرASCII الموارد URI. تأكيد أن القيمة المفكورة مقارنة مع `params.uri`.
4. كسر سلسلة الاستماع المحدودة قبل استجابتها النهائية. إعادة إصدارها مع JSON-RPC أدوات تحديد المعلومات وإعادة التوصيل
5. إضافة مسدس سير العمل صريح إلى أداة النقاش. ربطها بموضوع الإذن دون استخدام صلة الاتصال.
