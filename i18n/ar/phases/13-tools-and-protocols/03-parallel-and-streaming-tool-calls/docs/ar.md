# مكالمات الأدوات المتوازية وتدفق الأدوات

> ثلاثة عمليات بحث عن الطقس المستقلة المسلسلة هي ثلاث رحلات ذهابًا وإيابًا. قم بها بالتوازي وتنهار الوقت الإجمالي إلى أبطأ مكالمة واحدة. يصدّر كل مزود حدودي الآن مكالمات أداة متعددة في جولة واحدة. الجائزة حقيقية؛ والسباكة ظريفة. يدور هذا الدروس في النصفين: التمويع الموازي والحجة المتوصلة إعادة التجميع، مع التركيز على فخ الاصمة.

**Type:** Build
**Languages:** Python (stdlib, thread pool + streaming harness)
**Prerequisites:** Phase 13 · 02 (function calling deep dive)
**Time:** ~75 minutes

## أهداف التعلم

- اشرح لماذا `parallel_tool_calls: true` وجوده ومتى تعطيله
- ربط قطع الحجج المتدفقة مع الهوية الصحيحة للدعوة خلال التشغيل الموازي.
- إعادة تجميع الجزئي `arguments` السلاسل إلى كاملة JSON بدون تحليل مبكر
- إشغلي مقياس طقس ثلاث مدن يظهر التسلسل مقابل التخفيف المتوازي.

## المشكلة

بدون مكالمات متوازية، يقوم وكيل يجيب على "ما هو الطقس في بنغالورو وتوكيو وزيورخ" بهذا:

```
user -> LLM
LLM -> call get_weather(Bengaluru)
host -> run executor, reply with result
LLM -> call get_weather(Tokyo)
host -> run executor, reply with result
LLM -> call get_weather(Zurich)
host -> run executor, reply with result
LLM -> final text answer
```

ثلاثة LLM رحلات ذهاب و ذهاب، كل منها يدفع أيضاً تأخير المنفذ، حوالي أربع مرات الوقت المثالي للسيارة.

مع المكالمات المتوازية:

```
user -> LLM
LLM -> call get_weather(Bengaluru); call get_weather(Tokyo); call get_weather(Zurich)
host -> run all three executors concurrently, reply with three results
LLM -> final text answer
```

واحد LLM الرحلة الدوامية. وقت تنفيذ هو الحد الأقصى من الثلاثة، وليس المجموع. OpenAI, Anthropicو Gemini يظهر 60 إلى 70 في المائة من خفض الساعة الجدارية على عبء العمل المنتفخ.

السعر هو تعقيد التواصل عندما تكون المكالمات الثلاثة خارج النظام، يجب أن تكون نتائجك تتطابق مع `tool_call_id` عندما تتدفق النتائج، يجب عليك تجميع قطع الحجج الجزئية إلى كامل JSON قبل الإعدام Gemini 3 إضافة هويات فريدة في جزء لحل مشكلة في العالم الحقيقي حيث مكالمات متوازية إلى نفس الأداة كانت لا يمكن التمييز.

## المفهوم

### إمكانية التشابه

- **OpenAI.** `parallel_tool_calls: true` على افتراضياً `false` للاضطراب المتسلسل
- **Anthropic.** متوازية عبر `disable_parallel_tool_use: false` (الوضع الافتراضي على Claude 3.5 وما فوق) `true` لسلسلة
- **Gemini.** دائماً متوازية `tool_config.function_calling_config.mode = "AUTO"` دع النموذج يقرر.

إيقاف التوازي عندما تكون لدى الأدوات اعتمادات ترتيب (`create_file` ثم `write_file`), عندما تكون خروج مكالمة واحدة تُخبر مدخلات أخرى، أو عندما لا يستطيع مقيّد المعدلات التعامل مع إفراز المروحة.

### التواصل بين

كل مكالمة التي يصدرها النموذج لديها `id`كل نتيجة يعودها المضيف يجب أن يحتوي على نفس الهوية بدون هذا النتيجة غير واضحة

- **OpenAI.** `tool_call_id` على كل رسالة أداة
- **Anthropic.** `tool_use_id` على كل `tool_result` -بلوك
- **Gemini.** `id` على كل `functionResponse` (Gemini 3 أعلى Gemini 2 متطابقة باسمها التي انفصلت عن مكالمات متوازية ذات الاسم نفسه).

### إجراء المكالمات في وقت واحد

يدير المضيف تنفيذ كل مكالمة على خيطه الخاص، coroutine، أو عامل عن بعد. أسهل الحزام يستخدم حوض الخيط؛ إنتاج يستخدم asyncio مع `asyncio.gather` أو التزامن المهيكلي. ترتيب الانتهاء غير متوقع  هو المعرف.

خطأ شائع واحد: الإجابة بالنتائج في ترتيب قائمة المكالمات بدلاً من ترتيب الانتهاء. هذا عادة ما يعمل لأن النموذج يهتم فقط `tool_call_id`، ولكن إذا تم إلقاء النتيجة أو تكرارها ، فإن إرسال خارج النظام يجعل التحليلات الأصعب. يفضل الإجابة بالترتيب الكامل مع هويات صريحة.

### مكالمات أداة التدفق

عندما يتدفق النموذج `arguments` ثلاث تدفقات منفصلة من قطع لثلاث مكالمات متوازية تتداخل على السلك.

شكل من قبل المقدم:

- **OpenAI.** كل قطعة هي `choices[0].delta.tool_calls[i].function.arguments` (السلسلة الجزئية) الجزء يحمل `index` (موقع في قائمة المكالمات). تتراكم لكل مؤشر، قراءة `id` عندما يظهر لأول مرة، ويقومون بالتحليل JSON عندما `finish_reason = "tool_calls"`.
- **Anthropic.** الأحداث التدفقية هي `message_start`، ثم واحد `content_block_start` لكل كتلة مع النوع `tool_use` (يحتوي على الهوية والاسم والمدخل الفارغ) `content_block_delta` الأحداث تحمل `input_json_delta` -كلا، كلا `content_block_stop` يغلق كل حي
- **Gemini.** `streamFunctionCallArguments` (Gemini 3 وما فوق) يُصدّر قطع مع `functionCallId` لذا دعوات التقاطع نظيفة. Gemini 3، التسجيلات العريضة ردت مكالمة كاملة واحدة في كل مرة.

### جزئي JSON " والفخ " المفتاح " في وقت مبكر .

لا يمكنك تحليل `arguments` حتى يتم اكتمالها جزئيًا JSON مثل: `{"city": "Beng` لا يطابق مع الموقع و سوف يرفع. البوابة الصحيحة هي إشارة نهاية المكالمة من مقدم المكالمة: OpenAI- نعم `finish_reason = "tool_calls"`, Anthropic- نعم `content_block_stop`أو Geminiحدث نهاية التيار فقط بعد ذلك حاول `json.loads`. نهج أكثر قوة يستخدم JSON المصفح الذي يعطي الأحداث عندما تنتهي الهيكل OpenAIدليل التسجيل يوصي بهذا UX يظهر مؤشر "التفكير" الحي. لا يمكن الاعتماد على حساب العصا كاختبار الكمال (العصا داخل السلاسل المقتبسة أو المحتوى المنفصل يسبب إيجابيات خاطئة) ويجب استخدامها فقط كحكم تحذير غير رسمي.

### الإكمال خارج النظام

```
call_A: fast API, returns first
call_B: slow API, returns second
call_C: median API, returns third
```

يجب على رد المضيف أن يذكر الهويات:

```
[{role: "tool", tool_call_id: "call_A", content: ...},
 {role: "tool", tool_call_id: "call_B", content: ...},
 {role: "tool", tool_call_id: "call_C", content: ...}]
```

النظام في الرد لا يهم من أجل الصواب OpenAI أو Anthropic. Gemini تقبل أي طلب طالما أن هوياتها مطابقة

### المرجعية: متتالية مقابل متوازية

الحزام في `code/main.py` يحاكي ثلاثة تنفيذيات مع تأخر 400، 600، و 800 ms. التسلسل يديرها في 1800 ms إجمالي. متوازي يديرها في max(400, 600, 800) = 800 الفرق ثابت وليس متناسب، لذا فإن المدخرات تزداد مع عدد الأدوات.

تحذير في العالم الحقيقي: مكالمات متوازية تنشط أسفل النهر APIs. سوف تفشل عملية التوصيل إلى خدمة محدودة بالمعدلات عبر 10 طرق. تتناول المرحلة 13 · 17 الضغط الضغط على مستوى البوابة.

### التدفق المروحة خارج ساعة الحائط

إذا كان النموذج نفسه تدفق، يمكنك البدء في تنفيذ فور حجة واحدة من المكالمات اكتملت، بدلا من الانتظار لجميع المكالمات لإنهاء. OpenAI الوثائق ولكن ليس كلها SDKs يُعَمِلُ ذلك الحُلَمُ في هذه الدروس: بمجرد أن يُعطي التيار المُحاكِرُ كائنَ حجةٍ كامل، يُطلق المضيف تلك الدعوة.

## استخدمها

`code/main.py` يستخدم الأول ثلاثة مكالمات موسمية محاكاة تسلسليًا وموازية باستخدام `concurrent.futures.ThreadPoolExecutor` والنصف الثاني يعيد استجابة التدفق مزيفة `arguments` لثلاث مكالمات متوازية متداخلة على تيار واحد  وإعادة تجميعها لكل ID مع `StreamAccumulator`لا , لا LLMلا شبكة، فقط منطق إعادة التجميع.

ما الذي يجب أن ننظر إليه:

- الزمات التسلسل يصل إلى 1.8 ثانية و الزمات المتوازية يصل إلى 0.8 ثانية على نفس التأخيرات المزيفة
- المجموعة تتعامل مع قطع تصل خارج النظام عن طريق التخزين لكل الهوية وتحليل فقط عندما كل مكالمة JSON لقد اكتملت
- يبدأ الإنفاذ بمجرد أن تنتهي حججات الهوية، وليس بعد أن تنتهي جميع التدفقات.

## التمارين

1. أركض `code/main.py` وتغير التخميسات المثبتة. تأكد أن النسبة الموازية إلى التسلسل هي تقريبا `max/sum` (الدورات الحقيقية تختلف قليلاً عن المثالي بسبب جدولة الخيوط والتسلسل والتكامل الجوي). في أي توزيع التأخير يتوقف التضامن الموازي عن التضامن؟

2. تمديد الاكمبيوتر للتعامل مع حالة "تم إلغاء المكالمة في منتصف التيار" عن طريق إسقاط حافظةها وإصدار `cancelled` أي مزود يثبت هذه الحالة صراحة؟ Anthropic- نعم `content_block_stop` الإجمالي OpenAI- نعم `finish_reason: "length"` السلوك

3. استبدل حوض الخيط `asyncio.gather`يجب أن ترى أرباح صغيرة على async بسبب أقل تكلفة تغيير السياق، ولكن فقط إذا قام المنفذون بإجراء إدخال / إدخال حقيقي.

4. اختر اثنين من الأدوات التي يجب أن NOT التوازي (مثل `create_file` ثم `write_file`) إضافة `ordering_dependency` هذا هو الحد الأدنى من الآلات لتنظيم التوقيت واعي الاعتماد، والتي يتم رسمها في مرحلة مستقبلية من الهندسة العملية.

5. اقرأ OpenAI" قسم الاتصال بالعمل الموازي " و Anthropic- نعم `disable_parallel_tool_use` تحديد نوع واحد من أدوات العالم الحقيقي حيث Anthropic يوصي بإعاقة التوازي (تلميح: الطفرات التالية على نفس المصدر)
