# MCP 安全：投毒元数据、路由与 MRTR 状态

> 无状态不等于无须信任。它意味着每个请求都应给出服务器与网关独立验证调用所需的证据。

**Type:** 学习
**Languages:** Python
**Prerequisites:** 第 13 阶段 · 第 07 课（MCP 服务器）、第 13 阶段 · 第 08 课（MCP 客户端）
**Time:** 约 60 分钟

## 学习目标

- 将工具描述、注解、客户端信息和服务器信息视为不可信数据。
- 检测元数据投毒、描述符变化和跨服务器名称冲突。
- 验证 2026-07-28 请求元数据与 Streamable HTTP 路由请求头。
- 防止 MRTR `requestState` 被篡改，并将确认绑定到精确参数。
- 将授权和速率限制应用于主体，而不是已移除的协议会话。

## 问题

模型读取工具描述来决定调用什么；路由器读取工具名称来决定把请求发往何处；用户读取标签来决定批准什么。一个恶意描述符就能同时攻击这三者。

MCP 官方安全指南的态度很直接：除非描述和注解来自可信服务器，否则都应视为不可信。即便如此，部署信任也会发生变化。服务器更新、软件包被攻破、注册表配置错误或网关合并，都可能改变模型看到的内容。

当前协议也改变了安全边界。2026-07-28 中不存在核心握手和传输会话。仅以 `Mcp-Session-Id` 作为审批、速率限制或审计历史键的安全设计，已经不符合当前协议。

## 核心概念

### 值得检查的七个攻击面

使用具体清单，而不是含糊地要求“小心”。

1. **元数据投毒。** 描述中包含与所声明工具行为无关的指令。
2. **描述符偷换。** 已获批准的名称、描述、模式或注解发生变化。
3. **跨服务器遮蔽。** 两个后端公开相同的非限定工具名，路由却静默选择其中一个。
4. **请求头与正文混淆。** `Mcp-Method` 或 `Mcp-Name` 与 JSON-RPC 请求不一致。
5. **能力提升。** 对端声称支持某项扩展或客户端功能，而服务器误把该声明当成授权。
6. **MRTR 状态篡改。** 客户端更改 `requestState`、回答另一个问题，或把一次确认复用于不同参数。
7. **供应链身份混淆。** 把熟悉的显示名称当成发布者或服务器身份的证明。

这些攻击面彼此重叠。哈希固定有助于发现描述符变化，却无法证明第一版描述符是安全的；静态扫描能捕获明显措辞，却看不出隐晦指令；命名空间能避免一类冲突，却防不住恶意的命名空间服务器。应叠加使用多种控制措施。

### 当前请求信封是证据，不是身份

每个 2026-07-28 请求都包含：

```json
{
  "_meta": {
    "io.modelcontextprotocol/protocolVersion": "2026-07-28",
    "io.modelcontextprotocol/clientCapabilities": {
      "elicitation": {"form": {}}
    },
    "io.modelcontextprotocol/clientInfo": {
      "name": "security-lab",
      "version": "1.0.0"
    }
  }
}
```

每个请求都要验证版本和能力结构。能力用于选择兼容的响应结构。不要把 `clientInfo` 当成经过认证的主体，因为它只是自行声明的信息。

结果元数据中的 `io.modelcontextprotocol/serverInfo` 同样适用这一警告。它有助于日志记录和调试，但不是证书、注册表证明或授权决策。

### 先验证路由，再应用策略

对于 `tools/call`，Streamable HTTP 包含：

```text
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: notes.export
```

请求头中的方法必须等于正文方法，请求头中的名称必须等于 `params.name`。一旦不一致，应在选择后端、应用 RBAC 或消耗速率限制令牌之前，以 `-32020` 拒绝。

这种顺序消除了一种常见歧义：一个组件按正文授权，另一个组件却按请求头路由。

线协议验证遵循一套精确顺序。先验证 JSON-RPC 和元数据类型，再比较请求头与正文，最后检查匹配后的版本是否受支持。请求头不匹配时返回 HTTP 400 和 `-32020`。若请求头与正文一致、但版本不受支持，则返回 HTTP 400 和 `-32022`，且 `data` 必须精确为 `{"supported":["2026-07-28"],"requested":"<actual>"}`。未知方法返回 HTTP 404 和 `-32601`。

当合约需要结构化恢复信息时，每个错误对象都包含可选的 `data`。通知没有 `id`，所以永远不会收到 JSON-RPC 成功或错误响应。已接受的 HTTP 通知返回 202 和空响应体。

### 固定完整描述符

仅对描述做哈希会漏掉模式和注解的变化。应规范化并哈希用户批准过的描述符字段：

```python
normalized = json.dumps(tool, sort_keys=True, separators=(",", ":"))
digest = hashlib.sha256(normalized.encode()).hexdigest()
```

把摘要保存在 `notes.export` 这类限定键下，并在这个简化示例之外同时记录发布者证据与批准时间。

每次刷新时：

- 未知键：隔离，等待审查。
- 键相同但摘要不同：视为描述符偷换并隔离，直至重新批准。
- 非限定名称重复：要求使用确定性命名空间。
- 扫描器命中：阻止使用，并审查完整描述符。

哈希相等只证明内容稳定，不证明内容安全。被投毒的描述符即使被完美固定，也依旧有毒。

### 静态扫描用于触发预警

简单模式可以标记角色标签、指令覆盖、隐瞒行为、秘密访问和经过混淆的网络目标。其成本很低，适合在安装时和 CI 中运行。

它们不是语义安全证明。安全描述可能在合理警告中包含被标记的短语，恶意描述也可能避开所有短语。应把扫描器输出作为审查证据，而不是自动判定无害的分数。

### 合并前先加命名空间

假设两个服务器都公开 `search`，绝不能让发现顺序决定谁胜出。

```text
notes.search
issues.search
```

限定名称是公开的网关名称，后端映射则单独记录。稳定名称让审批、审计、哈希固定和 `Mcp-Name` 路由都指向同一个对象。

### 能力是兼容性声明

逐请求的 `clientCapabilities` 告诉服务器客户端能处理哪些协议功能。它不会授予客户端访问工具、数据或操作的权限。

授权仍来自已认证主体和资源策略。执行顺序如下：

1. 认证传输凭据。
2. 验证版本、请求头和请求结构。
3. 检查能力兼容性。
4. 授权主体、工具、资源与参数。
5. 执行，或请求用户输入。

### 保护无状态 MRTR 确认

会产生重大影响的工具可能需要用户确认。当前 MCP 使用 Multi Round-Trip Requests，而不是服务器到客户端的回调。

第一次响应：

```json
{
  "resultType": "input_required",
  "inputRequests": {
    "confirm": {
      "method": "elicitation/create",
      "params": {
        "mode": "form",
        "message": "Export notes to archive?",
        "requestedSchema": {
          "type": "object",
          "properties": {
            "confirm": {"type": "boolean"}
          },
          "required": ["confirm"]
        }
      }
    }
  },
  "requestState": "opaque-integrity-protected-value"
}
```

客户端获取输入，并使用新的 JSON-RPC ID 重试原始方法：

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "notes.export",
    "arguments": {"query": "private", "destination": "archive"},
    "requestState": "opaque-integrity-protected-value",
    "inputResponses": {
      "confirm": {
        "action": "accept",
        "content": {"confirm": true}
      }
    },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {
        "elicitation": {"form": {}}
      }
    }
  }
}
```

每个 `inputRequests` 值都是一个完整的嵌入式请求，带有 `method` 和 `params`。它的键必须与 `inputResponses` 中对应的条目匹配。表单征询使用对象根级别的 `requestedSchema`，且服务器请求表单征询前，客户端必须已声明相应能力。

当前能力有两种有效的表单声明。`{"elicitation":{}}` 隐式支持表单征询，而 `{"elicitation":{"form":{}}}` 显式声明支持。像 `{"elicitation":{"url":{}}}` 这样的仅 URL 声明不支持表单请求。服务器返回 HTTP 400 和 `-32021`，且 `data.requiredCapabilities` 等于 `{"elicitation":{"form":{}}}`。

把 `requestState` 视为敌对输入。对其签名或加密，验证其内容，并将它绑定到方法、工具、精确参数、用途、过期时间、主体，以及在重放风险重要时使用的一次性 nonce。本课代码使用 HMAC 和精确参数匹配，使这条边界清晰可见。

nonce 台账不得只存在于单个网关对象中。可运行模型注入了一个有界、按 TTL 清理的重放存储，可由多个网关实例共享。其原子认领操作就是执行边界：只有验证通过的接受操作或显式终止型拒绝才会消耗状态。格式错误的响应或 `cancel` 不执行任何操作，并在过期前保持可重试。生产集群同样需要在共享持久化存储中进行条件式认领。

不要把隐藏的确认上下文保存在协议会话中。任意服务器实例都应能够验证重试请求。

### 高风险调用的二项上限原则

从三个维度对一次调用分类：

- 它是否接收不可信输入。
- 它是否能访问敏感数据。
- 它是否会引发有重大影响的外部操作。

单个自动化步骤不应同时具备三项。应拆分操作、降低权限，或通过 MRTR 请求用户明确输入。这是一条设计启发式规则，不是协议能力。

### 执行前缩减权限

无状态本身并不等于安全。它移除了隐藏的协议历史，但一个自包含请求仍然可能要求权限过大的处理器泄露数据或做出不可逆变更。安全性来自在每一层边界缩减权限：

1. **类型化动词。** 公开 `archive_note` 这类有明确边界的操作，而不是可以表达无关能力的通用 `run` 或 `request` 工具。
2. **经过验证的参数。** 条件允许时使用封闭模式，拒绝未知字段，只规范化一次标识符，限制大小，并在评估策略前验证目标、租户和资源所有权。
3. **当前授权。** 将已认证主体绑定到精确的动词、资源、环境和规范化参数。工具注解与客户端能力不会授予这种权限。
4. **绑定操作的审批。** 对于会产生重大影响的调用，把审批绑定到类型化动词与规范化参数的摘要，并同时绑定主体、过期时间和一次性策略。任何字段变化都需要重新决策。
5. **一等拒绝结果。** 将拒绝、审批过期、用户拒绝和不安全目标建模为不执行副作用的普通结果。不要把拒绝转换成权限较弱的后备工具。
6. **脱敏审计证据。** 记录谁发起了请求、使用了哪个获准描述符与策略版本、授权了哪个规范化目标、为何允许或拒绝，以及是否开始执行。存储摘要或脱敏值，而非秘密。

每一步都会缩小下一个组件可执行的范围。最终处理器应接收已经验证的领域命令，而不是原始模型文本与宽泛凭据。在 MRTR 重试、任务更新或网关转发调用时，都要重复整条链路。较早的审批不会让后续请求变成可信的会话流量。

### 当前交互路径与旧版交互路径

Roots、Sampling 和 Logging 已不建议用于新的 2026-07-28 实现。网关只能把较旧的请求通道代码保留为按版本门控的兼容路径。

不要围绕逐会话 sampling 限制器构建新防线。应按照已认证主体、签发方、资源、工具和时间窗口应用配额。对于当前交互式工作，应检查 MRTR 输入请求与响应。

### 无状态传输检查

- 在单一 POST 端点接受现代 MCP 消息。
- 对现代 GET 和 DELETE 返回 405。
- 不签发也不依赖 `Mcp-Session-Id`。
- 不把旧版会话与重放请求头当作权限输入。
- 针对该 POST 返回 JSON 或请求作用域 SSE。
- 只将 `subscriptions/listen` 用于已选择启用的长时变更通知。

## 动手构建

`code/main.py` 实现了一个小型进程内安全网关模型。它规范化并固定完整工具描述符，报告元数据投毒与遮蔽，验证现代请求信封和路由值，并使用经过签名的 `requestState` 与注入的共享重放存储，执行需要两轮确认的导出。

模型从 HTTP 适配器已解析 JSON 正文和路由请求头之后开始工作。它不验证 `Content-Type` 或 `Accept`。可将同一分派器接入第 09 课的完整 Streamable HTTP 适配器；该适配器要求 `Content-Type: application/json`，并要求 `Accept` 的值同时包含 `application/json` 与 `text/event-stream`。

运行：

```bash
cd phases/13-tools-and-protocols/15-mcp-security-tool-poisoning
python3 code/main.py
python3 -m unittest discover code/tests -v
```

示例会故意修改一个描述符。扫描器和摘要比较会分别产生独立发现。随后，导出流程会演示 `input_required` 响应与无状态重试。

## 实际使用

把 `SAFE_TOOLS` 替换为来自你自己已批准服务器的规范化快照。不要在快照中放入凭据或秘密。更新摘要前，审查每个新增或变更的描述符。

在网关中，应在发现期间以及分派前再次运行相同检查。缓存可以减少发现工作，但已缓存的批准必须过期，或在描述符变化时失效。

## 练习

1. 将已认证主体和当前授权决策绑定到密封的 MRTR 状态，然后拒绝由另一主体发起的重试。
2. 用持久化条件插入替换内存重放存储，并证明两个进程不能同时认领同一个 nonce。
3. 在认领重放状态后、模拟导出前注入故障。定义并测试可确保安全恢复的事务或幂等性规则。
4. 在不更改描述的情况下修改工具的 `inputSchema`。确认完整描述符固定能够捕获它。
5. 添加一项策略：当 `tools/list` 因主体而异时，拒绝公共缓存。
6. 在网关后建模一台旧服务器。把所有握手和会话行为都放进显式的 `2025-11-25` 兼容分支。

## 关键术语

| 术语 | 含义 |
|------|---------|
| 元数据投毒 | 嵌入工具描述符中的指令或欺骗性声明 |
| 描述符偷换 | 对此前已批准描述符的更改 |
| 工具遮蔽 | 非限定名称重复导致的歧义路由 |
| 请求头不匹配 | 路由请求头与 JSON-RPC 正文不一致，错误码为 `-32020` |
| 哈希固定 | 完整已批准描述符的摘要 |
| MRTR | 用于服务器请求输入的无状态响应与重试模式 |
| `requestState` | 必须视为不可信输入的不透明往返值 |
| 能力声明 | 协议兼容性声明，而不是授权 |
| 隐式表单支持 | 空的 `elicitation` 能力对象，等价于支持表单 |
| 限定工具名 | `notes.search` 这样的稳定网关名称 |
