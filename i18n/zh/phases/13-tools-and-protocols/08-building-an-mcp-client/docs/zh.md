# 构建 MCP 客户端：发现、路由与双时代回退

> 现代 MCP 客户端会在每个请求中重复声明其契约。兼容性处理中最棘手的判断，是分清服务器确实属于旧版，还是现代服务器只是在报告一个可以修正的错误。

**Type:** 构建
**Languages:** Python
**Prerequisites:** 第 13 阶段 · 第 07 课（构建 MCP 服务器）
**Time:** 约 85 分钟

## 学习目标

- 为每个 MCP `2026-07-28` 请求附加当前元数据。
- 使用 `server/discover` 探测 stdio 服务器，并选择双方共同支持的版本。
- 仅对明确列入允许名单的对等端，授权一次有边界的旧版探测。
- 只有在验证支持修订版的有效 `initialize` 结果后，才接受旧版协议时代。
- 以确定方式合并工具列表，绝不悄然覆盖名称冲突。
- 将调用路由到拥有相应工具的对等端，同时不虚构协议会话。

## 问题

一个智能体宿主通常需要与多个 MCP 服务器通信。它必须发现各服务器、合并工具目录、处理重名、路由调用，并从传输故障中恢复。

`2026-07-28` 修订版让稳定运行阶段更简单，因为每个请求都能自我描述；但兼容性要求会让启动过程更加微妙。客户端可能遇到：

- 支持首选版本的现代服务器；
- 返回已识别版本错误或请求头错误的现代服务器；
- 从未听说过 `server/discover` 的旧版服务器；
- 在收到 `initialize` 之前始终保持沉默的旧版服务器。

把每一种探测错误都当成旧版信号很危险。现代请求格式错误、服务器过载、进程死亡和服务器版本陈旧，都可能表现为相同的超时或连接关闭。这些信号本身存在歧义。客户端在选择旧版协议时代之前，必须把运维人员的明确意图与肯定的协议证据结合起来。

## 概念

### 对等端，而非协议会话

为每个服务器进程或端点维护一条传输对等端记录：

- 传输句柄或发送函数；
- 已选定的协议时代与版本；
- 最近一次发现的服务器能力；
- 最近一次获得的确定性工具列表；
- 用于关联响应的待处理请求 ID；
- 传输健康状态。

这些只是客户端侧的记录，并不是协议会话状态。在现代 MCP 中，服务器仍会在每个请求中收到当前版本与能力。

### 每次都从头构建现代请求

```python
def modern_request(request_id, method, params, version, capabilities):
    return {
        "jsonrpc": "2.0",
        "id": request_id,
        "method": method,
        "params": {
            **params,
            "_meta": {
                "io.modelcontextprotocol/protocolVersion": version,
                "io.modelcontextprotocol/clientCapabilities": capabilities,
                "io.modelcontextprotocol/clientInfo": CLIENT_INFO,
            },
        },
    }
```

不要只把元数据附加到连接对象一次，便假定它已经传到线路上。应在最终序列化请求中写入元数据，并检查实际发送的内容。

### 现代协议发现

`server/discover` 会返回受支持版本、服务器能力、说明、缓存提示，以及建议使用的服务器身份。客户端应选择双方共同支持的最高现代版本。

对于只支持现代协议的客户端，发现步骤可以省略，但在 stdio 上建议执行。一些旧版服务器会在初始化之前接受操作，因此先发送 `tools/list` 可能得到含义不明确的成功结果。`server/discover` 能划出清晰的协议时代边界。

### stdio 兼容性探测

兼容两个协议时代的 stdio 客户端，应在发送任何其他请求之前，先用首选的现代元数据发送 `server/discover`。结果分为三类：

1. **DiscoverResult。** 服务器属于现代协议。选择双方共同支持的版本，然后继续使用逐请求元数据。
2. **已识别的现代错误。** 服务器属于现代协议。对于 `-32022`，从 `data.supported` 中选择版本，并用新的请求 ID 重试。对于请求头或能力错误，则修正请求。不要发送 `initialize`。
3. **歧义信号。** 未识别的 JSON-RPC 错误、超时、连接关闭或空响应，都无法确定协议时代。除非这个特定对等端已配置为允许旧版兼容，否则应以关闭方式失败。

已识别的现代协议错误包括：

- `-32020` HeaderMismatch
- `-32021` MissingRequiredClientCapability
- `-32022` UnsupportedProtocolVersion

即使对等端位于旧版允许名单中，已识别的现代错误仍然证明它属于现代协议。一旦服务器表明自己理解现代错误词汇，再发送 `initialize` 就会构成降级。

不要把 `-32601` 当作肯定的旧版证据。它只能让明确列入允许名单的对等端获得一次旧版探测资格。超时、连接关闭或空响应也遵循同一规则。

### 允许名单表达运维意图，而非协议证据

旧版兼容性必须是某个固定对等端配置上的显式属性：

```python
client.add_server("archive", archive_transport, allow_legacy=True)
```

应将该选择绑定到配置的命令或端点。不要使用通配符，让任意服务器都能主动选择较弱的语义。没有设置 `allow_legacy=True` 的对等端，在出现含义不明确的发现结果后必须失败，并且绝不能收到 `initialize`。

允许名单只授权探测，并不决定协议时代。客户端应在传输层强制执行的截止时间内发送一次 `initialize`，随后要求同时满足以下全部条件：

- 响应使用 JSON-RPC `2.0`，并带有匹配的请求 ID；
- 只包含一个 `result`，且不包含 `error`；
- `protocolVersion` 位于客户端配置的旧版修订集合中；
- `capabilities` 字段的值为对象；
- `serverInfo` 是对象，其中 `name` 和 `version` 都是非空字符串。

超时、连接关闭、错误响应、结果格式错误、ID 不匹配或修订版不受支持，都必须以关闭方式失败。只有结构有效的肯定结果才能选定旧版协议时代。代码会把 `legacy_probe_timeout_ms` 传给传输适配器；真实的 stdio 或 HTTP 适配器必须强制执行该截止时间，不能只把它记录下来。

应为该传输对等端缓存已经选定的协议时代，不要在每次调用之前重复探测。

### 旧版是一条兼容性分支

一旦有边界的探测返回有效且肯定的旧版证据，客户端就严格按照所选旧版修订的定义工作：

1. 验证响应信封与关联 ID。
2. 验证协商出的修订版属于配置的旧版集合。
3. 记录已验证的能力与服务器身份。
4. 仅在所有检查通过后发送 `notifications/initialized`。
5. 在该传输的整个生命周期内使用旧版请求形态。

这条分支用于与已知对等端互操作，不是新服务器或新请求的默认设计。传输重启或端点改变后，应丢弃对等端的协议时代缓存并重新协商。

### 发现并缓存工具

对每个活跃对等端调用 `tools/list`。现代结果包含 `resultType`、`ttlMs` 和 `cacheScope`。应在正确的授权上下文内遵守新鲜度提示，并在过期或收到已订阅的列表变更事件后重新获取。

如果旧版服务器的响应缺少 `resultType`，客户端必须将其视为 `"complete"`。不要要求较早协商时代的响应带有现代缓存字段。

服务器应按确定顺序返回结果。客户端在合并之前也应排序，避免本地注册表顺序受进程启动时序影响。

### 安全处理冲突的命名空间合并

两个服务器都可能公开 `search`。应选择并声明一种策略：

1. **冲突时加前缀。** 保留第一个规范名称，后续冲突项则公开为 `<server>/<tool>`。
2. **冲突时拒绝。** 不加载重复项，并给出清晰的配置错误。
3. **悄然覆盖。** 永远不要采用这种策略；它会隐藏模型所选操作究竟发往哪个服务器。

同时保存规范名称与本地名称。模型看到的是规范名称；发出的 `tools/call` 则使用所有者服务器声明的本地名称。

### 路由调用

路由就是一次纯查找：

```text
canonical tool name
  -> peer name + local tool name
  -> new JSON-RPC request id
  -> modern request metadata or explicit legacy shape
  -> matching response id
```

拥有工具的传输不可用时，不要发送调用。应重新连接或重启传输，再次执行发现与 `tools/list`。如果操作安全策略允许，现代协议中因传输中断而丢失的在途请求，可以换用新的 JSON-RPC ID 重试。

### 通知与订阅

现代列表与资源变更只会出现在客户端打开的 `subscriptions/listen` 流上。客户端发送通知过滤器，等待 `notifications/subscriptions/acknowledged`，并通过通知元数据中的监听请求 ID 关联事件。

断开连接后，使用新的监听请求重新打开数据流，并重新获取相关列表或资源。现代数据流不使用 `Last-Event-ID` 恢复。

### 服务器不得主动发起请求

现代服务器不会为了采样、信息征询或根目录而向客户端发出独立 JSON-RPC 请求。它们会返回 `input_required`，客户端满足其中嵌入的输入请求后，再重试原请求。

满足输入请求时，不要阻塞对等端的响应读取器。应保留关联关系，并为重试创建新的 JSON-RPC ID。

```figure
tp-client-merge
```

## 投入使用

`code/main.py` 使用进程内的对等端函数，让协议决策保持可见。它连接两个现代对等端和一个有意列入允许名单的旧版对等端，然后合并并路由它们的工具。传输可调用对象会收到超时预算，因此兼容性分支无法藏起一次无界探测。

```bash
cd code
python3 main.py
python3 -m unittest discover tests -v
```

测试覆盖了普通演示容易遗漏的边界：

- 现代请求会重复携带元数据；
- 遇到 `-32022` 时会重试现代发现，而不会初始化；
- 即使对等端位于允许名单中，已识别的现代错误也绝不会导致降级；
- 未配置允许名单时，超时、连接关闭、空响应和未识别错误都不会触发 `initialize`；
- 只有获得有效且受支持的 `initialize` 结果后，位于允许名单中的对等端才会转为旧版；
- 格式错误或不受支持的旧版结果会让对等端保持不可用；
- 成功选定的协议时代会在传输生命周期内缓存。

## 练习

1. 让一个模拟服务器返回 `-32022`，但不提供双方共同支持的版本。确认客户端直接失败，而不是发送 `initialize`。
2. 将模拟旧版服务器加入允许名单，让它的有边界 `initialize` 探测超时，并证明对等端仍处于 `unknown` 且不可用。
3. 为两个授权上下文添加 `cacheScope: "private"` 的工具列表。确认客户端绝不会把其中一个上下文的缓存结果分享给另一个上下文。
4. 将冲突策略改为拒绝，并让启动过程报错，错误中应包含两个对等端的名称。
5. 添加一个有限的 `subscriptions/listen` 模拟器。数据流中断后，用新的请求 ID 重新监听并重新获取工具。

## 关键术语

| 术语 | 含义 |
|------|---------|
| 对等端 | 客户端为某个服务器传输及其发现数据维护的记录 |
| 协议时代 | 现代逐请求元数据语义或旧版初始化语义 |
| 发现探测 | 用于识别 stdio 协议时代的初始 `server/discover` |
| 已识别的现代错误 | 能证明现代协议行为并禁止回退到旧版的错误 |
| 旧版允许名单 | 运维配置，允许针对某个固定对等端执行一次有边界的兼容性探测 |
| 肯定的旧版证据 | 针对明确支持的旧版修订，获得有效且关联正确的 `initialize` 结果 |
| 合并命名空间 | 所有活跃对等端的规范工具名称集合 |
| 冲突策略 | 对重复工具名称添加前缀或予以拒绝的规则 |
| 协议时代缓存 | 为某个传输对等端保存的现代或旧版行为选择 |
| 传输恢复 | 重启或重连、重新发现、重新列举，并使用新 ID 安全重试 |
